# 提交契约

活动页提交信息与文件的完整约定。**活动页不直接调用这些端点**——它经桥接层由宿主
代发（见 `docs/bridge-protocol.md`）。这份文档描述的是宿主与后端之间的契约。

## 两个端点

### `POST /api/v1/events/{event_id}/submissions` — 纯字段

```
Content-Type: application/json          ← 强制
Idempotency-Key: 8f3a...                ← 可选

{ "name": "张三", "grade": "1" }        ← 请求体本身就是提交内容，没有信封
```

**强制 `application/json`** 同时是一条免费的 CSRF 防线：跨站表单只能发
form-urlencoded / multipart / text-plain，发不出这个类型。非该类型返回 `415`。

### `POST /api/v1/events/{event_id}/submissions:files` — 字段 + 文件

```
Content-Type: multipart/form-data

payload = {"name":"张三","grade":"1"}   可选，JSON 字符串
files   = <文件>                         可重复，可多个
```

**这是超集。** 需要"字段 + 文件"的活动页**只发这一个端点**，不要分两次调用——
否则同一次提交会在管理端显示成两条记录。SDK 会按有无文件自动选择，活动作者视角
永远是一次调用。

### 查询参数（两个端点通用）

| 参数 | 说明 |
|---|---|
| `kind` | 可选的自由标签，见下方规则 |
| `client_id` | 匿名标识，由宿主附加。**不是凭据**，仅用于分组 |

## `kind` 规则

`kind` 不做语义校验，但它会进入文件路径，因此**必须**受限：

- 允许 `[a-z0-9_-]`，长度 1–64
- 不符合（含大写、点号、路径分隔符、超长）时**回落到 `_default`**，而不是拒绝整次提交
- 该值**不影响路径的任何上级目录**

## 幂等

**只有一条机制：请求头 `Idempotency-Key`。**

| 机制 | 触发条件 | 作用域 |
|---|---|---|
| 幂等键 | 请求头 `Idempotency-Key` 相同 | 活动内（不同活动可复用同一个键） |

命中时返回 `201` 且 `deduplicated: true`，`submission.id` 指向首次创建的记录，
**不新建行、不消耗配额**。

幂等检查在配额之前。顺序很关键：若在配额之后，一个反复重试的客户端会在自己已经
被去重的情况下把名额撞满。

### 为什么不再按内容哈希去重

早期版本还有一条"同一提交者在 300 秒内提交相同内容视为重复"的兜底。它被**移除**了：

那条规则**不看请求身份、只看内容相似度**，因此会误伤真实场景 —— 用户提交「表单 +
照片A」后发现传错，改成「**同样的表单** + 照片B」重提，第二次会被判定为重复并
**连同附件一起静默丢弃**，而用户看到的是"已经收到过了"。

两种失败模式的代价不对等：

| | 可见性 | 可恢复性 |
|---|---|---|
| 重复留下两条记录 | 管理员看得见 | 可恢复（删掉即释放名额） |
| 误判丢弃提交与附件 | **用户与管理员都看不见** | **不可恢复，用户以为成功了** |

所以宁可偶尔多一条记录，也不要静默吞掉一次提交。

**代价**：防连点现在完全由活动页承担（提交时禁用按钮）。`Idempotency-Key` 覆盖的是
"同一个请求被重传"，不覆盖"用户点了两次"—— 每次点击是一个新的意图，应当用新的键。

## 提交者标识

| 情形 | `submitter` |
|---|---|
| 已登录 | `u:{user_id}`（由服务端会话推导，客户端传值无法覆盖） |
| 匿名 | `a:{client_id}`，**必需** |

**匿名提交必须带 `client_id`。** 缺它时返回 `422 validation_failed`，而不是回落成
`a:unknown` —— 回落会让同一活动下所有匿名提交塌缩成同一个提交者，管理端无法区分、
按提交者的分组与统计全部失真。走 SDK 的活动页不会缺它（`clientId` 由宿主持久化）。

**匿名标识不是凭据。** 它可以被伪造也可以被清除，因此不能用于鉴权。直接后果是：
**匿名用户没有"我的提交历史"**，读取历史必须登录。

## 审核状态

三条状态，**存整数码值**。码值是对外契约的一部分 —— 导出与筛选都按它走，改动必须
配迁移。

| 码值 | 名称 | 含义 |
|---|---|---|
| `0` | 不采用 | 管理员看过并决定不要 |
| `1` | 待处理 | 新提交的默认值，尚未决定 |
| `2` | 已采用 | 管理员接受 |

刻意**没有"审核中"这一档**：三档已经够用，而中间态会让"按状态筛选"多出一个语义
模糊的桶 —— 管理员要么还没看，要么已经决定。

「不采用」取 `0` 而不是别的，是因为它在布尔与数值判断里天然表示"否"。**因此下游
筛选时不能用 `status || 默认值` 这种写法** —— 那会把 `0` 悄悄当成"没给"。

### 状态与名额无关

标记为**不采用不会释放名额**。计数器统计的是实际存在的行，要腾出名额只能删除。
这一点在管理端界面上有明确提示，因为"拒绝了就等于处理完了"是很自然的误判。

### 批量改状态
```
POST /api/v1/admin/submissions:review
{ "ids": [1, 2, 3], "status": 2 }        →  { "reviewed": 3 }
```

与 `:delete` 对称，存在的理由是**省掉逐条往返**：管理端会把跨页挑选的条目攒成一条
队列再统一处理，逐条 `PATCH` 就是几十个请求，而它们本该是一次事务。取回这些行只用
一次 `IN` 查询，不随条数增长。

`ids` 上限 500 条（与 `:delete` 一致），性质是**让一次请求的代价可预期**，不是安全
边界。

**找不到的 id 直接跳过，不报错**，`reviewed` 返回的是**实际改动数**。批量操作多半
是"管理员勾了一批、期间有人删掉了其中一条"，为了那一条让整批失败，管理员无从判断
哪条出了问题，只能重试。调用方拿到 `reviewed < ids.length` 时应当提示差异。

## 内容搜索

管理端列表可以按内容做子串搜索：

```
GET /api/v1/admin/events/{event_id}/submissions?q=张三
```

**搜的是整份 payload 的文本，不是某个字段。** payload 没有字段级契约（活动自己决定
放什么），平台无从知道该搜哪个键，所以按子串在序列化后的内容里找 —— 字段名、字段值、
`$display` 都在其中。空串等同于"没给"。

### JSON 按**不转义**的形式落库

这一点是搜索能不能用的前提。默认的 `json.dumps` 会把中文写成 `\uXXXX`，于是库里
存的是 `\u5f20\u4e09`，而人搜的是"张三" —— **搜中文永远匹配不上**，功能看起来在、
实际对中文完全无效。

因此引擎配置了 `json_serializer` 使用 `ensure_ascii=False`。这同时消除了另一处早就
存在的不一致：体积校验用 `canonical_json`（不转义）算字节数，而库里存的是更长的
转义形式。读回来完全一样，所以这是一次纯粹的存储形态修正。

既有的行由迁移 `7d1b16f0e498` 就地还原，否则搜索会变成"老数据搜不到、新数据搜得到"。

### `%` 与 `_` 会被转义

它们是 SQL `LIKE` 的元字符。不转义的话搜 `%` 会匹配全部记录 —— 用户想找一个百分号，
却拿到整张表。这类"静默地给了错误答案"比报错难查得多，所以搜进去之前先转义。

## 单个提交者的份数上限

活动可以声明 `max_per_submitter`（留空不限，下限 1）。达到上限的提交者再提交时返回
`409` 与 `submitter_quota_exhausted` —— **刻意与活动满额的 `quota_exhausted` 分成两个
码**：活动满额是"整个活动没位置了"，个人满额是"你不能再交了，别人还可以"，活动页
给出的提示也该不同。

### 计数为什么是一张表，而不是数一下

"这个人交过几份"完全可以从 `submissions` 数出来，但那是**读一下再写**：

```
T1: 数到 0 → 允许        T2: 数到 0 → 允许
T1: INSERT               T2: INSERT        → 两份，而上限是 1
```

同一段代码在不同库上表现不同：SQLite 下第二个写者撞快照冲突报错（安全但难看），
MySQL 的可重复读下两个请求各自数到 0、**双双插入，静默超限**。

所以计数放在 `submitter_quotas(event_id, submitter, used)` 上，用单语句 CAS 更新，
与活动级配额同一套理由与形状。每次提交多一次单行 upsert —— 相比写 payload 与落盘
文件，这是噪声；换来的是任何隔离级别、任何数据库都成立。

### 计数器永远在走

即使活动没设上限，计数也照常维护。这样管理员**以后才设上限**时不必再回填一次，
也不会出现"设上限之前交的那些不算数"。升级到该版本的迁移会按既有提交回填一次。

### 删除要退还

与活动级配额同一条理由：不退还的话，管理员删掉一条也救不回那个人。单条删除递减，
批量删除按实际行数重算（重算也是这个计数的自愈入口）。

注意退还的语义是"份数减一"，不是"立刻腾出一个位置"：某人若因上限下调而处于限额
之上，删掉一条只是让他更接近下限，要减到低于上限才真的能再交。

### 对匿名提交，这条限制只是建议性的

限额按 `submitter` 计，而它的取值分两种：

- **登录用户**：`u:{user_id}` —— 服务端确定，可信
- **匿名**：`a:{client_id}` —— **客户端自己生成并传上来的**，换一个浏览器就是一个
  新的提交者

也就是说匿名活动的"每人限 1 份"防的是误操作，**防不住故意绕过**。要真正限制，得把
活动设成 `submission_requires_login`。管理界面有相应提示——不写清楚的话，管理员会
以为它是硬限制。

## 存储布局

```
字节    data/{event_id}/{kind}/{yyyy}/{mm}/{uuid}{ext}     私有，绝不静态暴露
元信息  submission_files 表（原名、大小、sha256、嗅探类型、存储状态）
内容    submissions 表（payload、幂等键、状态码）
```

原始文件名**只作为元信息**，绝不参与路径构造。下载时经鉴权端点，响应强制
`Content-Disposition: attachment` 与通用二进制类型。

## 错误码

| `error.code` | 状态 | 含义 | 客户端该做什么 |
|---|---|---|---|
| `login_required` | 401 | 活动要求登录 | 引导登录 |
| `event_closed` | 403 | 未发布 / 未到开放时间 / 已截止 | 渲染"已截止" |
| `quota_exhausted` | 409 | 名额已满 | 渲染"名额已满"，**不再展示表单** |
| `rate_limited` | 429 | 触发限流 | 提示稍后重试（唯一值得重试的） |
| `validation_failed` | 422 | 内容不合规，`error.fields` 给出字段级信息 | 标注到对应输入框 |
| `payload_too_large` | 413 | 内容或文件超出体积上限 | 提示压缩或减少文件 |
| `unsupported_media_type` | 415 | 非 `application/json` | 修正请求类型 |
| `not_found` | 404 | 活动不存在 | 停止 |

**`409` 与 `429` 的区别是刻意的**：前者是终态，后者是"稍后重试"。用 `429` 表示
名额已满会诱导客户端重试一个永远不会成功的请求。

## 体积与数量上限

| 配置项 | 含义 |
|---|---|
| `MAX_PAYLOAD_BYTES` | 规范化序列化后的内容上限 |
| `MAX_UPLOAD_BYTES` | 单文件上限 |
| `MAX_FILES_PER_REQUEST` | 单次请求文件数上限 |
| `MAX_REQUEST_BYTES` | 整个请求体上限（另有一道 nginx `client_max_body_size`） |

超限请求**不留下任何已落盘文件**：已写入的部分会被清掉，数据库那侧整体回滚。

## 配额

- 可匿名提交的活动默认封顶 **4096 条**（`MAX_SUBMISSIONS_PER_EVENT_ANON`）
- 需登录的活动默认**不限额**（`MAX_SUBMISSIONS_PER_EVENT_AUTHED`）
- 活动可用 `max_submissions` 覆盖；`0` 是合法值，表示谁都不能提交
- 达到上限返回 `409` `quota_exhausted`
- **管理员删除提交会释放名额**，这是满额活动唯一的自救手段

配额由单语句 CAS 维护，并发提交不会突破上限；写入失败时名额随事务回滚。
