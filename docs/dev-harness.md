# 本地开发集成测试台

给活动页作者与平台开发者。目标只有一句话：**让"活动页 ↔ 宿主"的完整链路在本地就能跑通，
而不是等到投放之后**。

## 两个目录，两种东西

这是这份文档最要紧的一节。两个目录都装活动页，但装的是不同阶段的东西：

| | `events/` | `content/` |
|---|---|---|
| 是什么 | 活动页**源码** | **投放产物** |
| 谁写进去 | 你，直接编辑 | 管理台上传 zip 后解压而来 |
| 版本控制 | **入库** | 排除（运行时数据） |
| 服务地址 | `/draft/**`，**仅开发模式** | `/content/**` |
| 生命周期 | 你说了算 | 下一次投放**整体替换** |

`content/` 之所以不适合当工作台，不只是"没入库"：投放在同一条目录上做整体替换 ——
先把现目录改名成 `.previous`，再把新解压的内容顶上来，然后删掉 `.previous`。也就是说
**你手写在那里的文件会在下一次投放时消失**。作者的工作台恰好是部署的目标位置，这是
之前最容易踩的一个坑。

> `events/` **不是**第二条投放路径。上线仍然只走管理台 zip。让源码目录直接生效会引入
> 第二个"线上是什么"的来源，而那个问题一旦有两个答案，就不再能从任何单一来源推断。

## 放一个草稿页

```
events/<name>/index.html          <- 入口，名字固定
events/<name>/assets/notes.json   <- 同目录的其它资源，相对路径照常
```

访问：

```
http://localhost:5173/draft/<name>/index.html
```

相对路径的资源同理，`./assets/notes.json` 会解析到
`/draft/<name>/assets/notes.json`。

想绕开前端、直接确认服务端那一侧是不是对的，就直连后端：

```
http://127.0.0.1:8000/draft/<name>/index.html
```

两个地址应当返回同一份内容。**若前端那个返回的是应用外壳（SPA 的 HTML），说明
`vite.config.ts` 里的 `/draft` 代理没生效** —— 它被 history fallback 接住了，
而症状看起来像"草稿页坏了"。

## 草稿页与线上页面的能力完全一致

这是刻意的，也是这套东西能替代"投放后再看"的前提。草稿挂载与内容投放**走同一条
服务端管线**，因此草稿页同样具备：

- **通配的跨源许可头** —— 处于不透明源的沙箱页面对同主机也算跨源。少了这个头，
  草稿页连自己目录下的 `assets/notes.json` 都取不到。
- **桥接脚本自动就位** —— 你不写 `<script src="/sdk/v1/cea.js" id="cea-sdk">`
  那一行，服务端也会在返回 HTML 时补上；自己写了就不重复注入。

如果这两件事里少了任何一件，本地验证就证明不了线上的行为 —— 而"证明得了"正是
在这里先跑一遍的全部理由。

## 调试用的活动：`dev`

调试台要有一个**已发布**的活动才能工作：活动信息走的是公开接口，而未发布的活动在
那上面是 404 —— 于是草稿页连活动信息都取不到，更别提提交。

因此开发模式启动时会补齐一个活动（标识 `dev`，可用 `DEV_EVENT_ID` 改）：

| 属性 | 取值 | 为什么 |
|---|---|---|
| 状态 | **已发布** | 未发布的活动在公开接口上不可见 |
| 可见性 | **不可见** | 不该让每个开发者本机的首页都多出一个假活动；但按标识仍能直接打开 |
| 登录要求 | 免登录 | 打开调试台就能直接提交成功，不必先去管理台改配置 |
| 名额上限 | 用默认值 | 不在补齐时覆盖，把"改配额"留给需要它的那次调试 |
| 标题 | 含「仅本地」 | 它会和真实活动并排出现在管理台列表里，名字要能一眼看出用途 |

**它会出现在管理台的活动列表里**，这是刻意的：它是一条真实的记录，藏起来反而会让人
在别处看到它时更困惑。改配置、删掉它都可以 —— 下次启动只在它**不存在**时才补，
不会覆盖你改过的任何东西。这一点是有意的：把名额上限设成 0 看终态、打开「需登录」
看 `login_required`，是调试台最常用的两个动作，每次重启都重置回去就等于把它们废掉。

想验证某个特定配置时，不必改它，直接把调试台指到别的活动：

```
/develop?event=2026autumn&src=/draft/mytest/index.html
```

## 只在开发模式存在

`/draft` **只在 `APP_ENV=development` 时挂载**。其他模式下这个前缀根本没有挂上，
请求会得到 404，而不是"挂上了再拒绝"。上面那个调试活动同理：非开发模式下启动
**不会创建任何活动**。

判据是"等于 `development`"，不是"不等于 `production`" —— 用后者的话，任何拼错或
未预期的取值（`staging`、`Production`、空串）都会意外获得一份公开可读的草稿内容面，
以及一个凭空出现的已发布活动。

因此有两件事要记住：

1. **改完后端代码要重启后端。** 挂载与补齐都发生在应用启动时，不是每次请求时。
2. **生产环境该前缀由 nginx 明确返回 404**，理由与 `/data` 相同：不能让一个开发
   专用的前缀在生产上返回 200 的应用外壳，那看起来像"这里有东西"。

## 越界与私有性

草稿目录是公开只读的，和 `content/` 一样：**任何能访问到的人都能读到页面里的全部
内容，包括注释与内联脚本**。不要把口令、密钥、内部链接写进草稿页。

请求路径里含向上跳转（`../`、`%2e%2e` 等）一律 404，不能逃出草稿根目录。

## 调试台面板

打开调试台后，左边是承载你页面的沙箱 iframe；右边是内容区，**最右侧**是一条**工具轨**。
轨上是图标，点一下切一页 —— 这样每一页各自装得下，不必在一条长列里来回滚：

| 页 | 作用 |
|---|---|
| 状态 | 来源、活动标识、是否已握手、待决请求数、过滤与默认应答的当前状态、挂起数 |
| 身份 | 冒充已登录 / 显示名 / 该活动是否要求登录 |
| 动作 | **协议里每一个宿主消息类型**一个按钮，清单从 `protocol.ts` 推导 |
| 拦截 | 多选过滤、默认应答、以及挂起的请求队列（**轨上有角标**） |
| 日志 | 双向消息，含类型、请求 id 与关键载荷 |

只有「日志」与「拦截」两页里的**流式内容**（日志列表、挂起队列）会自己滚动 —— 那是它们的
正常形态，与"整块面板一条长滚动"不是一回事。

拦截页的角标值得留意：它是唯一**需要有人去做点什么**的页。挂起的请求不会自己消失，而活动页
正在那边等着。

### 身份那一页改的是什么

它只改**下发给活动页的身份描述符**，以及宿主"提交前登录短路"的判据。真实会话仍然是
浏览器的 Cookie，所以"冒充已登录"不会让后端认你 —— 它用来测的是活动页在两种身份下
渲染得对不对，以及 `login_required` 短路会不会按预期在**发出请求之前**返回。

### 日志里几种来源，不能混着看

| 标记 | 含义 |
|---|---|
| `活动页 →` | 活动页发给宿主的消息。在宿主的来源校验与信封校验之后观测到，**是真实的线上消息** |
| `宿主 →` | **宿主自身**发出的消息（初始化、会话推送、应答、通知、确认框……）。在宿主真正 `postMessage` 的那一处观测到，同样真实 —— 所以"活动页请求"与"宿主应答"能成对看到 |
| `面板 →` | 面板直接发出的宿主侧消息。真实的发送（与 `宿主 →` 分开，只是为了看出"这条是我手动点的"） |
| `假响应 →` | 面板伪造的那条结算。**没有发往任何后端** |
| `挂起` | 被拦下来、还没决定的请求。不是消息，是队列状态 |

`宿主 →` 这一类需要宿主暴露一个**只读**观测口子（`BridgeHostOptions.onMessage`）：结果是宿主发出的，而沙箱 iframe 不含 `allow-same-origin`，宿主对 `contentWindow` 的属性访问会抛 SecurityError —— 包装 `postMessage` 做不到。

### 拦截：挂起，然后你来选

拦截分三步，缺一步都不成立：

1. **多选过滤**决定**哪些操作**会被拦。没勾中的一律照常转发 —— 所以"一个都不勾"与没有这个功能完全一样。
2. 命中的请求**不会发给后端**，它停在挂起队列里，界面把它的操作名、请求 id 与**完整参数**摊开给你看。
3. 你来选：**假响应**（造一个错误回给活动页，后端毫不知情）或**转发**（照常发给后端，把后端的真实返回值回给活动页）。

不想逐条点，就把**默认应答**打开并选一个动作 —— 命中的请求按该动作直接结算，不进队列。
默认应答**默认是关的**：开着会让"拦截"从一个观察动作变成静默改写结果的动作。

> **为什么必须是"挂起"，而不是早先那种"抢先应答"。**
> 早先的做法是让请求照常发出去、面板抢先回一条伪造结果。那样做不到上面第 2、3 步：你看到
> 请求时它**已经发出去了**，所以既没法"看清再决定"，"转发"也不成为一个选择（无论选什么，
> 后端都已经收到了）。挂起才有真正的选择。
>
> 代价是宿主上多了一个**行为**口子（`shouldHold` / `onHold`）。它安全的唯一理由是
> **生产宿主不传它** —— 传了的话生产请求可能被静默丢弃，活动页永远等不到结果，而服务端
> 什么都没收到、没有任何日志。`views/event/sandbox.spec.ts` 有一条断言钉住这一点。

挂起的请求**不进超时**：它等的是人的决定，而人可能去看别的东西了。

### 但"能真造的失败"仍然应该真造

假响应改的是"活动页怎么渲染这个结果"，不是"发生了什么" —— 这一点没有变，只是现在它连
"请求已经发出去了"这个副作用也没有了。

仍然建议：把开发活动的名额上限设成 0 就能拿到真的 `quota_exhausted`；把截止时间设到过去
就能拿到真的 `event_closed`。假响应留给真造不出来的那几个：`timeout`、`unsupported_op`、
`validation_failed`。
