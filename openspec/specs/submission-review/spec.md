# submission-review Specification

## Purpose

让管理员查看、筛选、审核与清理各活动收到的提交，使活动结束后信息能够被复核、导出与整理，并让误收或恶意内容可以被移除且释放配额。

## Requirements

### Requirement: 提交列表与筛选
管理员 SHALL 能够按活动分页查看提交，并可按分类标签、审核状态、提交者与时间范围筛选。列表 MUST 显示提交者标识、是否来自登录用户、提交时间与文件数量。

#### Scenario: 按活动查看提交
- **WHEN** admin 请求某活动的提交列表
- **THEN** 返回该活动的提交，分页可翻页

#### Scenario: 按分类标签筛选
- **WHEN** admin 以某分类标签筛选
- **THEN** 结果只包含该标签的提交

#### Scenario: 按审核状态筛选
- **WHEN** admin 以已采用状态筛选
- **THEN** 结果只包含该状态的提交

#### Scenario: 区分登录与匿名提交
- **WHEN** 检视提交列表
- **THEN** 能看出每条提交来自登录用户还是匿名访客

### Requirement: 审核状态流转
每条提交 SHALL 具有审核状态，取值为**待处理、不采用、已采用**三档，并在存储中表示为整数码值（分别为 1、0、2）。码值是对外契约的一部分，导出与筛选按它进行。管理员 SHALL 能够变更状态。状态变更 MUST 被记录时间与操作者。

系统 MUST NOT 提供"审核中"一类的中间态：中间态会让"按状态筛选"多出一个语义模糊的桶，而管理员要么还没看，要么已经决定。

#### Scenario: 标记为已采用
- **WHEN** admin 将某提交标记为已采用
- **THEN** 该提交状态码变为 2，并记录操作者与时间

#### Scenario: 标记为不采用
- **WHEN** admin 将某提交标记为不采用
- **THEN** 该提交状态码变为 0，且该提交仍存在于列表中

#### Scenario: 码值 0 仍可被筛选
- **WHEN** admin 以不采用（码值 0）筛选
- **THEN** 结果只包含不采用的提交，而不是被当作"未提供筛选条件"

#### Scenario: 非法状态被拒绝
- **WHEN** admin 提交一个不在取值范围内的状态
- **THEN** 请求被拒绝，且**没有任何一条**提交被改动

#### Scenario: 新提交的初始状态
- **WHEN** 活动页提交信息成功
- **THEN** 该提交的初始状态为待处理（码值 1）

### Requirement: 批量审核
管理员 SHALL 能够以**单次请求**将多条提交改为同一状态。该请求 MUST 只校验一次状态取值，且取回这些提交 MUST NOT 随条数产生线性增长的查询。

对已不存在的 id，请求 MUST NOT 失败：跳过它们，并在响应中给出**实际改动的条数**，使调用方能够判断结果与预期是否一致。

#### Scenario: 一次请求改多条
- **WHEN** admin 一次为多条提交设置同一状态
- **THEN** 这些提交全部变为该状态，响应给出实际改动条数

#### Scenario: 其中一条已不存在
- **WHEN** 请求的 id 列表里包含已被删除的提交
- **THEN** 请求仍然成功，其余提交被改动，响应中的条数小于请求的条数

#### Scenario: 非法状态不产生部分生效
- **WHEN** 批量请求携带非法状态取值
- **THEN** 整个请求被拒绝，列表中任何一条都不被改动

#### Scenario: 批量审核不释放名额
- **WHEN** admin 批量将提交标为不采用
- **THEN** 活动的已用配额不变

### Requirement: 删除提交释放配额
管理员 SHALL 能够删除提交。删除 MUST 在同一事务内递减该活动的已用配额，使被删除的名额立即重新可用。删除 MUST 同时移除该提交关联的文件记录与文件内容。删除失败时 MUST NOT 发生部分递减。

#### Scenario: 删除后名额释放
- **WHEN** 某活动已满额，admin 删除其中一条提交
- **THEN** 该活动的剩余名额增加 1，且新提交可被受理

#### Scenario: 删除同时移除附件
- **WHEN** admin 删除一条带附件的提交
- **THEN** 其附件记录与文件内容一并被移除，且此后无法下载

#### Scenario: 删除失败不释放名额
- **WHEN** 删除提交的过程中发生错误并回滚
- **THEN** 配额计数保持原值，且提交仍然存在

#### Scenario: 批量删除后计数正确
- **WHEN** admin 一次删除多条提交
- **THEN** 配额计数与剩余提交条数一致

### Requirement: 管理端附件访问
管理员 SHALL 能够下载任意提交中的任意附件，不受提交者限制。附件列表 MUST 展示原始文件名、类型、体积与上传时间。

#### Scenario: 下载他人提交的附件
- **WHEN** admin 下载某匿名提交中的附件
- **THEN** 得到该附件的字节内容

#### Scenario: 附件元信息可见
- **WHEN** admin 查看某条提交
- **THEN** 能看到每个附件的原始文件名、类型、体积与上传时间

#### Scenario: 附件已缺失时的处理
- **WHEN** 记录存在但文件内容已缺失
- **THEN** 响应为 404 且不暴露服务器文件系统路径

### Requirement: 提交内容按原始形态展示
管理端 MUST 以原始键值形态展示提交内容，MUST NOT 假设字段语义、MUST NOT 因字段缺失或类型不符而拒绝渲染。

#### Scenario: 任意键值可读
- **WHEN** 某提交的内容包含平台事先不知道的键
- **THEN** 管理端仍完整展示该键值

#### Scenario: 嵌套结构可见
- **WHEN** 提交内容包含嵌套对象或数组
- **THEN** 管理端以可读形式展示其结构

#### Scenario: 空内容提交可读
- **WHEN** 某提交只有附件而没有字段内容
- **THEN** 管理端正常展示该提交及其附件

### Requirement: 提交内容搜索
提交列表 SHALL 支持按内容子串搜索（`?q=`）。匹配对象是**整份序列化后的 payload**，而不是某个具名字段 —— payload 没有字段级契约，平台无从知道该搜哪个键，因此字段名、字段值与派生出的展示值都在搜索范围内。空串 MUST 等同于未提供。

搜索词中的 LIKE 元字符（`%`、`_`）MUST 被转义。不转义时搜 `%` 会匹配全部记录 —— 用户想找一个百分号却得到整张表，这类"静默地给了错误答案"比报错难查得多。

JSON MUST 以**不转义**形式落库。默认的 `json.dumps` 会把中文写成 `\uXXXX`，于是搜中文永远匹配不上：功能看起来在，实际对这份平台最主要的内容完全无效。既有行 MUST 由迁移就地还原，否则会变成"老数据搜不到、新数据搜得到"。

#### Scenario: 按中文匹配
- **WHEN** 某提交的内容中含"张三"，以 `q=张三` 搜索
- **THEN** 该提交出现在结果中

#### Scenario: 匹配任意位置与字段名
- **WHEN** 搜索词出现在某个值的中间，或出现在某个字段名里
- **THEN** 该提交同样被匹配

#### Scenario: LIKE 元字符被转义
- **WHEN** 以 `q=%` 或 `q=_` 搜索
- **THEN** 只返回内容里真的含有该字符的提交，MUST NOT 返回全部记录

#### Scenario: 空串不筛选
- **WHEN** `q` 为空串或全为空白
- **THEN** 结果与未提供 `q` 时完全一致

#### Scenario: 与其它筛选共存
- **WHEN** 同时给出 `q` 与分类、状态或分页参数
- **THEN** 各条件以"与"的关系共同生效

#### Scenario: 搜索限定在当前活动内
- **WHEN** 两个活动中存在内容相同的提交，对其中的一个发起搜索
- **THEN** 只返回该活动下的提交

#### Scenario: 既有数据在升级后可被搜到
- **WHEN** 升级到引入该搜索的版本，库中已有以转义形式存储的中文内容
- **THEN** 该内容能被中文搜索词命中

### Requirement: 已删除账号的提交者显示
当某条提交来自一个已被删除的账号时，管理界面 MUST 显示它，而不是让管理员面对一个悬空的内部标识 —— 后者要求读者自己推断"这个 `u:7` 为什么查不到人"。显示内容是提交者标识本身（`u:<编号>`）加一个「已删除」标记：正文里不重复那层意思，而标识保持可用 —— 它正是筛选参数要用的值。

**提交列表与提交详情 MUST 显示同一件事。** 二者是同一份信息的两个视图，任何一侧漏掉标记都会让管理员在那一侧被误导；实现上 MUST 共用同一处渲染，MUST NOT 各写一遍。

**"来自已删除账号"与"匿名" MUST 被区分开，且 MUST 以互斥的标记呈现。** 前者是登录用户交的、只是那个账号不在了；后者是访客交的。二者都会让账号归属为空，但**把它们混为一谈会让管理员误以为那条提交是访客交的**。判定"是否来自登录用户" MUST 依据提交者标识本身，MUST NOT 依据账号外键 —— 账号删除时该外键会被清空，据此判断会让每一条来自已删除账号的提交都变成"匿名"。

平台 MUST NOT 因为提交者账号已不存在而隐藏该提交、改动其内容或阻止对其审核。"这条提交该不该显示"与"谁交的"是两个问题，前者不受后者影响。

解析整页提交者的账号状态 MUST 在一次查询内完成，MUST NOT 随页内条数线性增长。

#### Scenario: 账号已删除时显示标识与标记
- **WHEN** 提交列表中某条提交的提交者账号已被删除
- **THEN** 该行显示 `u:<编号>` 并带「已删除」标记

#### Scenario: 列表与详情显示一致
- **WHEN** 同一条来自已删除账号的提交分别在列表与本条的详情中查看
- **THEN** 两处显示相同的标识与相同的标记

#### Scenario: 已删除账号的提交不被标为匿名
- **WHEN** 某条提交来自一个已被删除的账号
- **THEN** 该处**不出现**"匿名"标记，而是出现"已删除"标记 —— 列表与详情皆然

#### Scenario: 匿名提交不被标为已删除
- **WHEN** 某条提交来自匿名访客
- **THEN** 该处出现"匿名"标记，且**不出现**"已删除"标记

#### Scenario: 账号仍在时显示不变
- **WHEN** 提交者的账号仍然存在
- **THEN** 该处显示其显示名，且两个标记都不出现

#### Scenario: 判定不依赖账号外键
- **WHEN** 某账号被删除（其提交的账号外键随之被清空）
- **THEN** 该提交仍被判定为"来自登录用户"，只是账号已删除

#### Scenario: 已删除用户的提交仍可审核
- **WHEN** 管理员对一条来自已删除账号的提交执行审核操作
- **THEN** 操作正常生效，与账号是否存在无关

#### Scenario: 解析不随条数增长
- **WHEN** 一页中混合了来自现存账号、已删除账号与匿名访客的提交
- **THEN** 解析这些提交者状态的查询次数与页内条数无关
