# Design

## Context

绿地项目。仓库当前只有三样东西：未改动的 Vue3 官方模板（`frontend/`）、仅有 `pip` 的 Python 3.13 虚拟环境（`.venv/`）、以及已初始化但为空的 OpenSpec 与 git。无既有系统、数据或接口需要兼容。

参见 `proposal.md` 了解动机。这里只列影响方案的约束：

- **活动页由各活动自行编写**，且既有参考实现是手写单文件 HTML（见 `D:\Ds_Projects\Documents\CEA\workspace\posters`），不是组件化应用。平台必须接受这种形态，而不是要求活动改造成某种框架页面。
- **活动页与 SPA 同源**（`/content` 与 `/` 由同一 nginx 提供），这让"隔离"必须靠浏览器机制主动建立，而不是靠跨域天然获得。
- **无邮件基础设施，但可能具备**。凭据验证与找回必须在此前提下两种路径都能走通。
- **单机部署**，SQLite，校园社团规模的流量。
- **预留向 MySQL 迁移**，因此任何依赖特定数据库行为的写法都要关进仓储层。

## Goals / Non-Goals

**Goals:**

- 建立一条从浏览器到数据库的信任链，使活动页能提交信息却**不持有任何可复用凭据**。
- 让"接受任意结构的提交内容"成为一个**安全**的选择，而不是把风险推给运行环境。
- 让数据访问层的数据库方言差异集中在一处，使 MySQL 迁移成为替换配置而非重写代码。
- 让限流在不引入共享存储的前提下覆盖来源与用户两个维度。

**Non-Goals:**

- 不追求活动页的强隔离（独立域名 / 独立源）。本设计在同一源内用沙箱建立隔离，不引入第二套 TLS 与 DNS。
- 不做表单字段级契约与服务端语义校验（见"决策 6"）。
- 不做基于数据库或 Redis 的分布式限流。
- 不实现邮件发送本身，只留接口与开发用替代实现。
- 不追求多进程横向扩展；本设计的并发模型建立在单进程之上。

## Decisions

### 决策 1：活动页零凭证，全部调用经宿主白名单代理

活动 iframe 不持有任何凭据。所有后端交互由宿主 SPA 代发，activity 页只能通过 postMessage 请求**预定义操作**。

```
  活动页 (iframe, 不透明源, 零凭证)
       |
       |  postMessage { op: 'form.submit', args: {...} }
       v
  宿主 SPA (持有 HttpOnly Cookie 会话, axios)
       |
       |  HTTPS  /api/v1/...
       v
  FastAPI
```

**为什么不用更简单的两种方案：**

| 方案 | 否决理由 |
|---|---|
| 原生会话标识直接 postMessage 给 iframe | 活动页与 SPA 同源且是组织者写的任意 HTML。它能顶用管理员会话调用任何接口，包括管理接口与用户管理。 |
| 为活动签发作用域受限的事件域令牌 | 可行且比方案一安全，但仍需新增令牌类型、签发端点与作用域校验，且活动页依然自己发请求，服务端无法在可信层拦截畸形数据。且它保留了"SPA 需要读取令牌"的需求，从而排除了 HttpOnly Cookie（见决策 4）。 |

**代价与收益：** 后端因此**更简单**——只有一种凭据、没有作用域令牌、没有签发端点。复杂度全部转移到前端桥接层，而那里本来就需要一个协议。额外白拿两项：上传进度由宿主上报（请求由宿主发出，进度天然可得）；提交前可先在可信层过一遍体积与结构约束。

**这条决策的唯一命门是白名单。** 如果宿主按活动页给的地址转发，就等于用宿主会话造了一个开放代理，安全收益归零。因此宿主只接受固定的操作名，且**活动标识一律由宿主自身路由决定，绝不采信活动页传值**。

### 决策 2：沙箱全强度，不含 `allow-same-origin`

```
  sandbox="allow-scripts allow-forms allow-modals allow-popups [allow-downloads]"
                                             ^
                                             +-- 绝不含 allow-same-origin
```

**为什么这是决策 1 的必需配套而非可选加固：** 没有沙箱时，同源 iframe 可以直接访问 `parent.document`，读到宿主内存里的状态，甚至移除自己身上的沙箱属性。此时"代理"只是一种礼貌约定，不是安全边界。

给出 `allow-same-origin` 会同时毁掉两边：iframe 既能碰父页面，又能自己摘掉沙箱。

**物理效果：** 不透明源发出的请求携带 `Origin: null`，对 `/api/**` 而言属跨源；而 `/api/**` 不返回任何 CORS 头，浏览器直接阻断。**代理因此从约定变成浏览器强制的边界**——活动页连尝试绕过都做不到。

### 决策 3：发送方校验用窗口引用，发送时不限定目标源

不透明源下宿主收到的消息其 `origin` 是字符串 `"null"`，用它做鉴权没有意义。

```
  宿主接收校验：  event.source === iframeEl.contentWindow     不可伪造
  宿主发送参数：  targetOrigin = "*"
  SDK 接收校验：  event.origin === 宿主源                      宿主是正常源，仍然有效
```

`targetOrigin: "*"` 在持有凭据的方案里是漏洞；**在这里之所以可接受，正是因为 iframe 什么都不持有**——泄露的只有公开活动信息与主题令牌。这是决策 1 换来的直接结果。

### 决策 4：会话用 HttpOnly Cookie（修订早期设想）

早期方案是"登录响应体返回令牌，前端存内存或 `sessionStorage`，用 `Authorization: Bearer`"。该方案的**唯一**理由是"SPA 需要读取令牌才能 postMessage 给 iframe"。决策 1 消除了这个需求，理由随之消失，结论应当反转：

| 存放位置 | JS 可窃取 | 刷新存活 | 跨标签页 |
|---|---|---|---|
| 内存 | 是 | 否 | 否 |
| `sessionStorage` | 是 | 是 | 否 |
| `localStorage` | 是 | 是 | 是 |
| **HttpOnly Cookie** | **否** | 是 | 是 |

三种脚本可读的存储在 XSS 面前**同等脆弱**，差别只是失窃后的存活期。HttpOnly Cookie 是唯一脚本读不到的，而决策 1 让"读得到"不再必要。

改用 Cookie 需要补 CSRF，而三重防护叠加后基本封死，其中第三条是为决策 2 已经付过的成本：

```
1. SameSite=Lax             跨站 POST 不携带 Cookie
2. 强制 application/json    跨站表单发不出这个类型（只能 form-urlencoded /
                            multipart / text-plain）
3. /api/** 无 CORS 头       跨站 AJAX 连预检都过不去（决策 2 已建立）
```

`Authorization: Bearer` **保留为等价认证路径**（约三行），供脚本、测试与将来的非浏览器客户端使用。

### 决策 5：`/content` 与 `/api` 的 CORS 刻意不对称

决策 2 的封锁链有一个必须补偿的副作用：不透明源**对同主机也算跨源**，因此活动页连取自己目录下的 `data.json` 都会失败。

```
  /content/**   ->  Access-Control-Allow-Origin: *
  /api/**       ->  不带任何 CORS 响应头
```

`/content` 是公开只读内容，加通配头不额外泄露任何东西；而 `/api` 保持无头，封锁链完整。**这个不对称是整个方案的支点**，必须同时写进 nginx 与 FastAPI 两侧配置，任何一侧漏了都会破坏其中一半。

### 决策 6：不做表单字段契约，后端接受任意结构的内容

活动页由各活动自行编写，形式各异。引入字段契约意味着要造一套字段描述方言、一个服务端校验器、一个表单编辑器与一套版本机制，而收益是**服务端字段校验**与**字段级错误定位**——这两项在活动页自己做校验时本就冗余。

**因此移除**：`event_forms` 表、字段方言、校验器、表单编辑界面、`schema_version`、`once_per_user` 去重、逐表单的登录要求与截止时间。

**因此保留**（这些不是契约，是安全与资源控制，丢弃代价是真问题）：

| 保留项 | 丢弃后的后果 |
|---|---|
| 文件体积、数量、请求总体积上限 | 任意人可写满磁盘 |
| 每活动字节配额 | 单文件有上限，但一个活动可以传一万次 |
| 活动存在性校验 | 为不存在的活动建出孤儿目录与孤儿行 |
| `kind` 路径消毒 | 客户端值进入文件路径 = 路径穿越 |

**"接受任意文件类型"之所以成立**，靠的是决策 8 的 `/data` 私有 + 附件强制下载头：上传的 `.html` 永远不被静态暴露，也永远不在浏览器中内联渲染。这两条缺一，本决策即不成立。

**失去的能力（明示）**：服务端不校验字段，活动页不校验则无人校验；管理端审核时只见原始 JSON，没有标签；历史数据无法回溯"当时的合法取值"。

### 决策 7：提交者标识为派生单列，匿名标识由宿主产出且不作凭据

```
  submitter = "u:{user_id}"     已登录，由服务端会话推导
              "a:{client_id}"   匿名，取客户端匿名标识
              "a:unknown"       匿名且未提供
```

**为什么要这个看起来冗余的派生列**：它是单列索引，"这个人在这个活动下的提交"一条查询即可命中，且登录与匿名两种情形语句完全一致。只用 `user_id` + `client_id` 就要写 `WHERE user_id=? OR client_id=?`，那个 `OR` 用不上索引且两种情形要分叉。

**匿名标识的来源**：沙箱下 iframe 没有存储，因此由宿主产出（`randomUUID`）、持久化于宿主 `localStorage`，并在初始化消息中下发。**不采信 iframe 回传的值**——否则一个写坏的活动页能把提交记到别的浏览器名下。虽然危害有限，但没有理由留这个污染入口。

**铁律：匿名标识不是凭据。** 它可被伪造也可被清除，因此**不能用于鉴权**。直接后果是：匿名用户没有"我的提交历史"，读取历史必须登录。正因它不是凭据，放进 XSS 可读的 `localStorage` 是安全的——这也是它与会话 Cookie 可以处在完全不同安全等级的原因。

### 决策 8：`/data` 私有，附件只能经鉴权端点读取

```
  /content/**   公开静态，ACAO:*       活动网页内容
  /data/**      私有：nginx 硬 404 且 FastAPI 不挂载
                唯一读取路径：鉴权端点 -> 仓储 -> 存储端口
```

下载响应强制 `Content-Disposition: attachment` 与通用二进制类型，**不回显客户端声明的内容类型**。这是决策 6 得以成立的前提：任意类型的上传内容都不会被浏览器当作页面执行。

存储实现放在 `FileStorage` 端口后（本地磁盘实现先行，对象存储可后补），使"读取路径唯一"这条约束在代码层面也只有一处出口。

### 决策 9：配额用计数器列 + 单语句 CAS

```
  UPDATE events SET submission_count = submission_count + 1
  WHERE id = :event_id AND submission_count < :limit
  -- rowcount == 0 即名额已满 -> 409 quota_exhausted
```

**为什么优于 `COUNT(*)` 方案**（后者也是可行且更"无状态"的）：

1. **可移植性是白拿的。** `COUNT` 方案要精确就必须在事务开始时取写锁，这需要仓储层写方言分支（SQLite `BEGIN IMMEDIATE` / MySQL `SELECT ... FOR UPDATE`）。CAS 是一条语句内的原子操作，任何隔离级别、任何数据库都成立——**迁移面少一个接缝**。
2. 不依赖隔离级别配置是否正确。
3. `quota.used` 变成已加载的列，活动详情这个高频只读接口不再跑聚合查询。

**性能不是选它的理由**：4096 条规模下 `COUNT` 走索引也是微秒级，两者都无关紧要。

**实现要点：**

- 上限值在 Python 侧由读到的活动行算出（该行第 1~4 步本来就要读），SQL 里只留一个绑定参数。**不把 `COALESCE(max_submissions, CASE WHEN ...)` 写进 SQL**——那样表达式要写两遍，且"不限"时 `submission_count < NULL` 恒为 NULL，表现为永久拒绝，极难排查。
- 先读活动行**不构成竞态**：读是为了取上限值（可能比管理员刚改的值差一个请求，可接受）；计数器的正确性由 SQL 里的比较保证。
- 用 `rowcount` 而非 `RETURNING`：SQLite 3.35+ 与 PostgreSQL 支持 `RETURNING`，MySQL 不支持。
- CAS 与插入放在同一事务：插入失败则整体回滚，计数自动回退，因此"写入失败占用名额"这一类漂移**无需额外处理即消失**。
- **单条删除必须在同一事务内递减**。这不是精度问题而是功能回归：管理员"删一条腾一个名额"是满额活动唯一的自救手段，不递减则活动被永久锁死且无法通过界面恢复。批量删除走重算，兼作唯一自愈入口。

**已知并接受的漂移**：手工改库造成的计数不一致不处理。

### 决策 10：限流两层，不做数据库限流

| 层 | 键 | 承担 |
|---|---|---|
| nginx `limit_req` | 客户端 IP | 最早、跨 worker 共享（共享内存）、零应用成本挡住洪流 |
| FastAPI 内存实现 | IP + 登录用户 | 能识别登录用户，可按端点细化 |

两层不是重复，**因为能拿到的键不同**——nginx 不知道请求属于谁。应用层因此能提供 nginx 给不了的按用户维度限流。

**为什么内存实现可以接受（通常不行）：**

`--workers N` 会让每个进程各持一份计数，实际阈值放大 N 倍。本设计选择 **`--workers 1`**——而这不是妥协：SQLite 的写入本就串行化在单写者锁上，多进程只增加锁争用而不提升写入吞吐。**单进程让内存限流在语义上完全正确**，同时 nginx 那一层已经覆盖 IP 维度。

**实现放在 `RateLimiter` 端口后**（内存实现先行，Redis 可后补），采用滑动窗口日志以避免固定窗口在边界处允许 2 倍突发。键的清理挂进既有的 janitor 任务，不引入新依赖（不用 `slowapi`，避免其与请求状态的耦合）。

**三个会静默失效的坑，必须按序处理：**

1. 不配 `--forwarded-allow-ips`，客户端自带 `X-Forwarded-For` 即可把限流键算到伪造地址上，应用层限流形同虚设。
2. nginx 前若有 CDN，`$binary_remote_addr` 变成 CDN 的地址——限流要么无效，要么封掉整个 CDN，需要 `real_ip` 模块。
3. `limit_req` 默认返回 503，语义错误，必须显式配 `limit_req_status 429`。

### 决策 11：`argon2` 只用于口令，令牌一律快哈希

| 用途 | 算法 | 理由 |
|---|---|---|
| 用户口令 | Argon2id | 口令是低熵的人类输入，必须靠慢哈希与内存硬度抵御离线爆破 |
| 会话凭据、重置/验证令牌 | `secrets.token_urlsafe(32)` + SHA-256 摘要存库 | 令牌本身已是 256 位随机，爆破不可行；且会话**每个请求都要校验**，用慢哈希会给每个请求平白加上几十毫秒 CPU |

一句话记法：**口令要"算得慢"，令牌要"猜不到"。** 两者与是否有邮件基础设施完全正交。

选 `argon2-cffi` 而非 `bcrypt`/`passlib`：bcrypt 在 72 字节处静默截断口令，长口令短语尾部熵丢失且不报错；`passlib` 事实上已停止维护，其 bcrypt 后端在 bcrypt ≥ 4.1 上会因 `__about__` 被移除而直接崩。

### 决策 12：凭据与验证令牌合表，两条签发路径共用兑换端点

```
  user_tokens ( purpose: 'email_verify' | 'password_reset' )
       ^                                    ^
       |                                    |
  自助路径（邮件可用）              管理员签发路径（邮件不可用）
  用户发起 -> 平台发链接            管理员签发 -> 线下转交
       \____________________________________/
                        |
                   同一兑换端点
```

无邮件设施不是降级为"没有找回功能"，而是切换到第二条签发路径。令牌**只存摘要**，明文只在签发响应中出现一次；一次性、有期限。

两个开关默认关闭，等邮件接上再逐一打开：`REQUIRE_EMAIL_VERIFICATION`、`ALLOW_SELF_SERVICE_RESET`。**邮箱验证绝不允许默认拦住登录**。

（此处曾列有第三个开关 `REGISTRATION_INVITE_CODE`，后经决策 19 移除。）

`EmailSender` 端口提供 console 实现，使开发环境无需 SMTP 即可跑通全流程。

### 决策 13：落盘与落库的一致性用状态列 + 清理任务

数据库提交与文件落盘无法组成一个事务，因此约定顺序并把中间态显式化：

```
  写字节 -> storage_state='pending' -> 提交数据库 -> 置为 'committed'
                                        |
                                   失败 -> 删除已写字节
  进程中断 -> 遗留 pending 记录 -> janitor 按状态回收
```

`storage_state` 是刻意加的：没有它，进程中断留下的残留无法与正常记录区分。janitor 同时负责过期会话、过期令牌与限流键清理，是唯一的后台清理入口。

### 决策 14：分层纪律与跨库可移植规则

```
  api/v1/*.py        只做 HTTP：解析、调用、组织响应
       v
  services/*.py      业务规则、事务边界、鉴权决策
       v
  repositories/*.py  纯持久化：SQLAlchemy 查询
       v
  db/models/*.py     只做 ORM 映射
```

两条硬规则，否则分层名存实亡：

1. **service 层不 import fastapi**，抛领域异常由 `errors.py` 映射为 HTTP —— 使 service 可脱离 HTTP 单测。
2. **repo 层不含业务判断**，只回答"存了什么"，不回答"能不能存"。

三个可替换端口由配置决定注入哪个实现：`RateLimiter`、`FileStorage`、`EmailSender`。

**迁移纪律（12 条中最容易漏的几条）：** `MetaData(naming_convention=...)` 统一约束命名（SQLite 忽略名字，MySQL 必须有名字才能 drop）；每个索引列显式 `String(n)`；写入前归一化（SQLite 的 `=` 区分大小写而 MySQL 默认不区分，唯一约束行为会分叉）；连接级 `PRAGMA foreign_keys=ON`（SQLite 默认**关闭**，缺少它 `ON DELETE CASCADE` 会静默失效并留下孤儿附件）；全 UTC 存储；方言 SQL 只出现在 repo 层；**Alembic 自第一个提交启用**。

### 决策 15：数据模型

```
  users ─┬─< sessions
         └─< user_tokens

  events ─┬─< submissions ──< submission_files
          │        ^
          │        └── submitter = u:{user_id} | a:{client_id} | a:unknown
          └── submission_count (计数器，CAS) / max_submissions (可空覆盖)
```

六张表。`submissions` 是"提交行为"本身，`submission_files` 挂其下（`ON DELETE CASCADE`）。纯文件提交的父行内容为空对象，因此不需要可空外键，也不需要第二张表。

**两个端点中文件端点是超集**：需要"字段 + 文件"的活动页只发一次 `:files`（`payload` 作为 multipart 的一个部分）。这保证了"一次提交 = 一行父行"，否则管理端审核会把同一次提交看成两条记录。SDK 按有无 `files` 自动选择端点，**活动作者视角永远是一次调用**。

**活动删除语义**：默认走 `archived` 状态（内容与数据保留，公开接口不可见）。物理删除仅由管理员显式发起，并级联移除内容目录与数据目录。

### 决策 16：内容投放为覆盖语义

一次内容包投放**整体替换**该活动的内容目录：先解压到临时目录，全部通过校验后再替换目标目录，`content_version` 递增。已投放但不在新包中的文件随之消失。

选择覆盖而非合并的理由：投放是一次**部署**而不是补丁，覆盖语义可预测（"目录内容 == 最后一次投放的包内容"），而合并会让"当前线上是什么"无法从任何单一来源推断。若将来需要增量更新单个文件，应新增独立的单文件上传端点，而不是把投放改成合并——否则同一个入口有两种互相矛盾的语义。

失败时的表现：校验不通过则临时目录被丢弃，**目标目录完全不被触碰**，`content_version` 不递增。

### 决策 17：内容包解压的防护顺序

zip 解压是唯一由外部内容驱动的写文件路径，防护必须**先校验后落盘**，而不是边解压边判断：

```
  1. 逐条规范化条目名，校验仍位于目标活动目录之内      -> 违规即整体拒绝
  2. 拒绝绝对路径条目与符号链接条目                    -> 违规即整体拒绝
  3. 校验条目数与解压后总体积上限                      -> 违规即整体拒绝
  4. 全部通过后才开始写入
```

先校验后写入保证了"检测到违规时活动内容目录不被修改"这一条可实现——边解压边判断会留下半成品。符号链接条目必须拒绝，否则上传者能用链接把 `/data` 或宿主任意文件读出去。

### 决策 18：首个管理员由启动引导创建，而非独立脚本

开放注册无法产生第一个管理员，因此必须有一条引导路径。

| 备选方案 | 否决理由 |
|---|---|
| 独立种子脚本，部署时手工执行 | 部署多一个易漏步骤；开发、测试与 CI 环境都要各自补一遍。漏掉之后表现为"系统一切正常但无人能登录"，排查成本高。 |
| 在数据库迁移中插入管理员行 | 迁移不应产生带口令的数据；迁移可重复执行（降级再升级），会把口令语义搞乱。 |
| **启动时检测用户表并引导** | 采用 |

**触发器是"用户表为空"，而不是"不存在名为 admin 的账号"。** 后者会在管理员被有意删除后，靠一次重启悄悄复活一个账号名已知的特权账号。

**这条与既有约束的交互使设计自洽：**

- `admin` 已在注册保留名清单中，没有人能抢先注册该名字。
- `user-administration` 规格中的"不能移除最后一个管理员"保证系统无法经由界面进入零管理员态。
- 两条合起来意味着引导路径在真实环境中**只在首次空库时执行一次**，此后永不触发。它不是一条长期存在的后门。

**口令的出口必须分两种，否则会留下一条默认落日志的路径。** 随机口令必须让人拿得到，但日志会被采集、转发、长期保留，不是可靠渠道：

```
  ADMIN_INITIAL_PASSWORD 未设置
      -> 生成高强度随机口令，仅在创建该账号的那一次以告警级别输出
         并提示首次登录后立即改密

  ADMIN_INITIAL_PASSWORD 已设置
      -> 使用该值，启动输出中完全不出现口令
```

后者是生产环境规避口令进入日志的正式手段，因此比"随机口令 + 打印"更完整。

**配置项：** `ADMIN_BOOTSTRAP_ENABLED`（默认开启）、`ADMIN_USERNAME`（默认 `admin`）、`ADMIN_INITIAL_PASSWORD`（默认为空即随机生成）。

**已知残留风险：** 引导创建的是**账号名可预测**的特权账号，登录限流（决策 10）与其口令强度是仅有的两道防线。因此注册保留名清单不可移除，否则 `admin` 可能被抢注，或出现同名普通账号造成混淆。

### 决策 19：注册分两阶段，用待验证占位保留用户名与邮箱

```
POST /auth/register         -> 202 + 建立 pending_registrations 占位 + 发出验证邮件
                               账号**此时不存在**
POST /auth/register/verify  -> 删除占位 + 创建账号（同一事务）
                               账号在**这一刻**才出现
```

**为什么不是"先建账号、再验证邮箱"。** 后者会给每一个写错邮箱的注册留下一个永远无法验证的账号 —— 它占着用户名、可能被用来登录（若验证不拦登录）、还得靠人工清理。两阶段把"邮箱写错"变成一个**什么都没发生**的结果，重来一次即可。

**为什么占位要同时锁住用户名与邮箱。** 不锁的话，两个人可以在同一分钟里用同一个用户名各自走到验证页，先点链接的那个赢了、另一个在最后一步才失败 —— 而他刚刚输入的一切都白费了。锁住之后冲突在**提交那一刻**就暴露，且两种冲突要分得清：

| 占用者 | 提示 | 用户该做什么 |
|---|---|---|
| 真实账号 | 已被注册 | 换个名字，或去登录/找回 |
| 另一条占位 | 有一条待验证的注册 | 查收邮件、等待过期、或换一个 |

只说"已占用"会让第二种情形里的用户跑去登录或找回 —— 而那个账号**根本不存在**。

**清理是承重结构，不是卫生工作。** 唯一性由唯一索引保证，而**索引不认时间**：一条过期的占位在被真正删除之前，会一直占着那个用户名和邮箱。因此清理必须做在两处：

- **请求时**：先删掉与新请求冲突的过期占位 → 预留**到期即刻释放**，用户不必等后台任务
- **janitor 兜底**：删掉全部过期占位 → 没人注册时也不会无限堆积（复用决策 13 的既有清理入口，不新起调度）

**核销用删除本身作 CAS，并与建号同事务。**

```sql
DELETE FROM pending_registrations
 WHERE id = ? AND expires_at > now AND token_hash = ?
-- rowcount = 1 -> 我拿到了，继续建号；= 0 -> 已被别人核销或已过期
```

一条语句内完成"校验 + 占用"，与决策 9 的配额 CAS 同一形状，任何隔离级别、任何数据库都成立。与建号同事务带来一个关键性质：建号失败（例如期间有真人抢注了该用户名）时整体回滚，**占位仍在**，链接在有效期内还能重试 —— 否则用户会既没建成账号又丢了凭据。

**刻意不引入 6 位验证码。** 曾考虑邮件里同时给验证码与链接，但那会连带引入：短码必须用 HMAC 摘要（6 位数字裸哈希一秒反查完）、尝试次数上限、以及一个匿名可爆破的端点。只留链接则这些都是多余的 —— 256 位随机令牌无法爆破，一次一用、十分钟过期。**少一个凭据，少一整类防护要写对。**

**移除邀请码（任务 4.8）。** 它在早期作为"默认关闭的开关"引入，但注册改为邮箱验证驱动之后，准入门槛由"邮箱可验证"承担；再叠一个共享口令既多余、又更难轮换 —— 一个人退出就得通知所有人换码。保留名清单与此无关，继续保留。

### 决策 20：邮件用浅色正文，纯文本与 HTML 同时发，不放图

三封信（注册核销、密码重置、邮箱确认）共用一套外壳，模板在 `app/services/email_templates.py` —— 纯函数，不碰数据库也不碰 Web 框架。

**浅色，而不是复刻站点的近黑底。** 站点的视觉语言是 `#0b0b0d` 底 + 品牌红，但邮件客户端对深色背景不友好：

| 客户端 | 行为 |
|---|---|
| Outlook（Windows，Word 渲染引擎） | 直接**忽略** `background-color` → 浅色文字落在白底上，几乎看不见 |
| Gmail / Apple Mail 暗色模式 | 可能**自动反色**整封信 → 深色邮件被翻成浅色，配色全乱 |

品牌感因此改由**品牌红（`#d0202f`）与等宽字体**承担 —— 这两样在任何客户端都稳。站点那套点阵纹理在邮件里也做不出来（不支持 `background-image`，且项目本身禁渐变）。

**两个版本都发。** `body` 是纯文本，`html` 是美化版，端口两个都收。只发 HTML 会被反垃圾系统扣分、纯文本客户端的读者会看到一片空白；只发纯文本则等于排版白做。**链接两边都必须有** —— 它才是这封信的用处。Resend 侧组装成 `multipart/alternative`；SMTP 侧用 `set_content` + `add_alternative(subtype="html")`，不写 `subtype` 会退化成 `text/plain`，客户端把整段 HTML 当正文原样显示出来。

**不放图片。** 多数客户端默认不加载远程图片，放了只是多一个空洞；邮件里的外链请求本身还是一个隐私面。头图那点收益不值得。

**布局用 `<table role="presentation">`。** 不是为了兼容 2005 年，而是因为 Outlook 至今用 Word 的渲染引擎，单列卡片写成 `div` + flex 在那边会散架。样式**只写行内**：Gmail 会剥掉 `<style>` 块，靠类名的排版到了那边就没了 —— 那是一种"本地看着好好的"的坏法。

**用户填的值必须转义。** 展示名是用户自己填的（"你好 {display_name}："）。纯文本时它只是排版问题，进了 HTML 就是注入 —— 用户能在平台发出的邮件里塞进任意标记。链接同样要转义，否则一个带引号的 URL 能逃出 `href` 属性。

**验证方式值得记一笔。** 排版没法靠断言说清好不好看，所以 `var/preview_emails.py` 把三封信导出成 HTML，再用无头 Chrome（`--headless --screenshot`）渲染成图肉眼核对 —— 转义那条路径也是这么确认的：`<img src=x onerror=alert(1)>` 在渲染结果里是**一行字**，不是一张图。

**幂等键不能从自增 id 派生（上线后踩到，任务 16.5.1）。** 键最初取的是占位行的 id（`registration-pending/{pending_id}`），而 `pending_registrations.id` 是 rowid 别名、**没有 `AUTOINCREMENT`**：一行被删掉（过期清理、或核销）之后，下一行会**拿回同一个 id**。于是两封内容不同的邮件撞上同一个键，Resend 判定为"改了内容的重放"直接拒收：

```
This idempotency key has been used with this HTTP method and endpoint
within the last 24 hours, but the request body was modified
```

表现是**注册接口照常返回 202，而那封信永远发不出去** —— 用户看到"请查收邮件"，邮箱里什么都没有，而且他重试多少次都一样。这正是"发信失败不影响接口结果"这条取舍的代价：它把邮件故障与注册流程解耦，但也意味着邮件故障**只能从日志里发现**。

修法是让键唯一对应**那一条消息**，而不是"那一行"：三封信统一用**令牌摘要**。每次签发都是一条新消息、摘要随之改变；而**同一条**消息若将来被重发（目前没有重发路径），摘要不变、正该被去重。**从行 id 派生则连重发功能都做不了** —— 一旦加了"重发验证邮件"，同一个 id 配新令牌，又会被服务端当成重放拒掉。

> 同一个坑在别处也成立：`users.id` 同样是 rowid 别名。这就是"用户删除"必须连带处理 id 复用的原因 —— 那里的后果是**新注册的人继承前一个被删者的提交与配额**。

## Risks / Trade-offs

**[沙箱限制活动作者能力]** → 不透明源没有 `localStorage`，`history.pushState` 抛异常，且不能直接 `fetch`。缓解：宿主经桥接代存草稿（不落后端，按活动隔离）；页内多步流程改用 hash；宿主在约定等待时间内未收到就绪消息时**明确提示缺少桥接脚本**，而不是留一片空白——这条比任何文档都管用。

**[无登录限流 ⇒ 在线口令爆破可行]** → 已启用应用层按来源限流覆盖登录与注册端点，并配套防枚举（失败响应一致 + 哑哈希校验）。风险降低但不为零，属明确接受的范围。

**[无字段校验 ⇒ 垃圾数据进库]** → 仅保留结构与体积约束。缓解：管理端按原始键值展示，管理员可据实际内容清理；`kind` 标签提供基本分组。

**[内存限流的跨进程失效]** → 由 `--workers 1` 消除，并在部署文档中写明该前提与其后果。

**[CAS 计数器漂移]** → 事务包裹消除"写入失败"这一类；单条删除配对递减消除"删除不释放"这一类；批量删除重算作为自愈入口。仅手工改库造成的漂移不处理。

**[`/content` 通配 CORS ⇒ 活动内容可被任意站点脚本读取]** → 内容本就是公开只读的，不构成额外泄露；但活动页**不得**在其中放置任何秘密（需在接入指南中明示）。

**[单进程限制吞吐]** → SQLite 写入本就串行，单进程与之一致；瓶颈先出现在磁盘与文件写入，而非进程数。

**[内容版本递增会失效既有缓存]** → 这是期望行为（改内容后活动页应重新加载），但意味着每次投放都让所有访问者重新下载入口页；入口页 `no-cache` 而带哈希的资源长缓存，把代价限制在单个文件。

**[zip 解压消耗磁盘与 CPU]** → 条目数、解压体积与压缩包体积三重上限；解压在校验通过后才开始。

**[两个配置面（nginx 与 FastAPI）必须同时正确]** → CORS 不对称、限流阈值、`client_max_body_size`、`/data` 屏蔽都分散在两侧。缓解：将这些约束集中记录在 `deploy/nginx/` 与接入指南中，并在实施时以端到端检查覆盖（沙箱内直接调 `/api` 必须失败、活动页取自身数据必须成功、`/data` 直取必须 404）。

## Migration Plan

绿地项目，无既有数据或接口需要迁移。

**首次部署顺序：**

1. 安装后端依赖（`.venv` 当前仅有 `pip`），执行 `alembic upgrade head` 建表
2. 以种子脚本创建首个管理员（开放注册无法产生第一个管理员）
3. 构建前端产物（含 SDK 独立构建入口）
4. 部署 nginx 配置：SPA history fallback、`/api` 与 `/content` 反代、`/data` 硬 404、`limit_req` 限流区、`client_max_body_size`
5. 以 `uvicorn --workers 1 --proxy-headers --forwarded-allow-ips <nginx 地址>` 启动并交由 systemd 管理
6. 端到端验证：匿名提交、登录提交、附件上传下载、配额头与释放、沙箱内直调 `/api` 被阻断

**回滚：** 无既有系统，回滚即停止服务。首次部署后 schema 变更一律走 Alembic 降级路径。

**后续 MySQL 迁移路径：** 更换连接串与驱动；仓储层的 upsert 写法切换；`PRAGMA foreign_keys` 连接钩子改为无操作；复核唯一约束在两库归一化行为上的一致性。由于方言 SQL 已全部关在仓储层、约束命名已统一、归一化已在写入前完成，预期为替换配置而非重写代码。
