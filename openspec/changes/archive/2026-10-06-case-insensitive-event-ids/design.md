# Design

## Context

活动标识同时承担四种角色，而它们对大小写的态度并不一致 —— 这是本变更全部复杂度的来源：

| 角色 | 现状 |
|---|---|
| URL 路径（`/{eventId}`、`/api/v1/events/{event_id}`） | 使用者可自由书写大小写 |
| 数据库主键 | 精确匹配（SQLite 字符串比较，无 `COLLATE NOCASE`） |
| 内容与数据目录名（`content/{id}/`、`data/{id}/`） | **取决于文件系统**：Linux 区分大小写，Windows/macOS 不区分 |
| 宿主存储命名空间（`cea.storage:{id}:{slot}`） | 前端自行拼接，**完全不经过后端** |

最后一行的存在决定了本变更不能只做后端归一化。动机见 `proposal.md`。

## Goals / Non-Goals

**Goals**

- 任意大小写的地址都能解析到同一个活动，且地址栏形态不被改写。
- 存储、目录名、存储命名空间**只存在一种形态**（小写），因此"仅大小写不同"的重名在物理上不可能出现 —— 包括在大小写不敏感的文件系统上。
- 既有活动与既有链接零影响。

**Non-Goals**（设计层面的边界，范围边界见 proposal）

- 不引入"显示用标识"与"存储用标识"两个字段。那会同时改表结构与全部接口，而本变更的目的只是让**输入**宽松。
- 不为标识引入规范化形式之外的任何转换（去重音、Unicode 折叠等）。

## Decisions

### 决策 1：归一化落在**使用这个键的那一层**，且**先归一化、再校验**

具体落点（**与原计划不同**，原因是实现中发现 API 层会直接调用仓储）：

| 落点 | 为什么是它 |
|---|---|
| `EventRepository` 各以 `event_id` 为键的方法 | 管理端的活动详情与内容清单**直接调用仓储**、绕过 service；仓储是这些调用的共同下游 |
| `SubmissionRepository.list_for_event` / `list_for_submitter` | 同上：管理端提交列表直接调仓储 |
| `ContentService.event_dir` / `data_dir` | 文件系统路径的唯一咽喉 |
| `EventService.create` | 唯一的写入口，且标识来自**请求体**而非路径参数 |
| 管理端两处响应回显 | 回显也取规范形态，调用方不必再归一化一次 |

**备选：集中到 service 层。** 部分否决 —— 这是最初的计划。实现时发现 `api/v1/admin.py` 有三处直接调用仓储，service 层的归一化覆盖不到它们，而漏掉的症状是**"空列表 + 200"**：管理端提交列表会看起来像"这个活动还没人提交"，没有任何提示。把归一化下沉到仓储，这些路径自动被覆盖。

**备选：只在 API 层加一个依赖做归一化。** 否决：分层纪律要求 `api` 不做业务判断；而且标识在**创建**时来自请求体而不是路径参数，路径依赖覆盖不到它。
- **备选：先校验再归一化。** 否决，而且这是本变更里唯一涉及**安全边界**的一步。标识直接成为目录名，若校验的是 `A` 而落盘的是 `B`，就出现"通过校验的值"与"实际使用的值"错位。实测确认小写化本身不会引入 `.`、`/` 或改变字符集（全角字母、`İ` 这类字符小写化后仍落在允许集之外而被拒），但**这个结论只在"校验的是归一化后的值"时才成立** —— 缺少这一步，路径安全就退化成"依赖某个语言 `lower()` 的具体行为"。

### 决策 2：归一化规则只做小写化，且必须在两端保持一致

规则是 `str.lower()` / `String.prototype.toLowerCase()`，不做别的。

- **备选：同时做 Unicode 归一化（NFKC）或去重音。** 否决：两端各写一次 `toLowerCase()` 的漂移风险可以接受，`NFKC` 之类不可以 —— 不同语言/版本的实现差异会变成"后端认得出、前端认不出"的间歇性故障。
- **备选：把规则实现成共享代码。** 前后端不同语言，做不到；退而求其次，两端各有一张**内容相同的样本表**用于断言（含全角、`İ`、带点号、空串等边界），并在两处注释里互相指向。规则一旦超出"仅小写化"，就必须改成单一实现，这条约束写进设计而不是留给后来者推断。

### 决策 3：不重定向到小写 canonical 地址

以大写打开活动时，地址栏保持大写。

- **备选：301/302 重定向到规范形态。** 否决：那会让"在 URL 里看到大写"这一诉求直接落空，而它正是本变更的目的。取舍是同一活动可以经由多种大小写到达（见 Risks）。
- **备选：只在首页与管理台生成小写链接，不管地址栏。** 这只是本决策的一个副作用，不是替代方案：地址栏形态由用户输入决定。

### 决策 4：前端归一化只放在**一处** —— 交给宿主的活动标识

`BridgeHost` 收到的活动标识在内部归一化一次，下游（初始化消息、`event.info`、`form.submit`、`storage.*`）全部走这个值。

- **备选：在各个调用点分别处理。** 否决：漏一处就是一个静默 bug，而最可能被漏掉的恰好是存储命名空间 —— 它的症状是"草稿凭空消失"，与大小写这个起因看起来毫无关系。
- **备选：等接口返回后用响应里的规范标识（`event.id`）。** 否决：活动页可以在 `CEA.ready` 之后**立刻**读写存储，那时活动信息还没到手；此时命名空间必须已经是对的，否则同一页面内会出现两个命名空间。响应里的规范标识仍有用（`hub:init` 下发它），但不能作为命名空间的唯一来源。

### 决策 5：`/content/**` 与保留前缀判定刻意不动

- `/content/{id}/…` 是静态挂载，按目录名精确取文件，无法也不该做大小写归一化。**它安全的前提是前端用接口返回的规范标识拼 iframe 地址** —— 若改成用路由参数拼，大写地址会让活动内容 404，这是决策 4 的一条具体理由。
- 保留前缀与路由匹配**实测已经大小写不敏感**（访问 `/Login` 得到登录框，静态路由胜出），`isReservedPath` 只被测试引用、并未接线。改动它没有可观察收益，因此不写 delta、不改代码。

## Risks / Trade-offs

- **同一活动存在多个可达 URL** → 接受。缓解：首页与管理台生成的链接一律是规范形态，大写只是"能被正确解析"，不成为被推荐的形态。
- **管理台创建时输入的大小写被改写** → 缓解：响应返回归一化后的标识（规格里已要求），界面据它显示，使改写可见而不是静默。
- **两端规则漂移** → 缓解：规则保持"仅小写化"这一种简单形态 + 两端样本表断言（决策 2）。
- **`/content/**` 的大小写行为不变，可能被误认为遗漏** → 缓解：写进本设计的 Non-Goals 与决策 5，并说明它安全的前提条件。

## Migration Plan

- **无数据迁移**：既有标识全部是小写，归一化对它们是恒等操作；列长度、索引与约束都不变。
- **部署即生效**，无顺序要求（不涉及迁移与服务重启的先后）。
- **回滚**：回退代码即可。回滚后大写地址恢复 404，期间产生的数据不受影响 —— 因为归一化从未写入过非小写值。
