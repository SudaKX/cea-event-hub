# Design

## Context

动机见 `proposal.md` 的 Why。这里只记约束与现状中影响做法的部分。

**既有的内容托管形状。** `/content/{event_id}/{path}` 由 `event-content-hosting` 规格钉住，其响应带通配跨源许可头，并在返回文档时保证桥接脚本就位。后端以一条静态托管管线同时承担这三件事（跨源头、缓存分档、脚本注入），而投放在同一条管线上做整体替换。这条管线是本次要复用的对象：草稿内容若绕过它，本地看到的能力集就与线上不同。

**写权限的分布。** `content/` 与 `data/` 被版本控制排除，理由是"运行时数据不进版本控制"。这使作者写活动页的位置恰好是投放的目标位置。

**既有的启动补齐先例。** 后端在启动时有一个一次性任务，用来补上"开放注册无法产生第一个管理员"这个缺口；它以库的某个状态为触发条件、幂等、可配置关闭，并且专门论证过"它不是一条长期存在的后门"（见 `docs/first-run-bootstrap.md`）。开发活动的补齐是同一类问题，因此沿用同一形状。

**前端的构建期能力目前未被使用。** 前端只用了两个自定义环境变量与基础路径，没有任何"仅在开发构建中成立"的先例。因此生产排除是一条新机制，必须实证而不能凭推断。

**既有测试的两条硬约束。**
1. 路由测试**从路由表推导**保留前缀清单，再断言每一项都登记在清单里 —— 于是"加一个开发构建才有的路由"会**强制**要求把它的前缀登记进清单（在测试环境里开发判据为真）。
2. 仓库已经有"清单从真源推导，而不是手写一份"的取向，理由写在路由测试里：两边各写一份时，往一边加东西却忘了同步另一边，测试照样绿。

## Goals / Non-Goals

**Goals**

- 让"活动页 ↔ 宿主"的完整链路在本地可跑，且跑的是**同一套**宿主语义与同一套内容管线。
- 让桥接的失败分支可以被**主动**复现，而不是靠碰巧。
- 让开发用的东西在构建期就从生产产物中消失，而不是靠运行时开关。
- 让活动页源码进入版本控制，与投放产物分开。

**Non-Goals**

- 不把 `events/` 变成第二条投放路径（见 proposal 的不做项）。
- 不改 `/content/**` 的任何语义。
- 不为调试台另实现宿主语义。
- 不追求"打开调试台就能模拟一切"：真后端能造出来的分支就让它真造。

## Decisions

### 决策 1：草稿内容挂到 `/draft/**`，来源是入库的 `events/`

**备选与否决理由**

| 备选 | 否决理由 |
|---|---|
| 把 `content/` 与 `/content/**` 一起改名 | `/content/{event_id}/{path}` 是规格明文钉住的契约。改名要同时动 nginx、前端的内容基址、保留前缀、文档与若干注释，收益只是名字更贴切 |
| 目录叫 `events/`，URL 也叫 `/events/**` | `events` 读起来像"活动内容总目录"，与 `/content` 的关系（源码 vs 产物）看不出区别；`/draft` 表达的是**状态**，正好补上缺失的那一层信息 |
| 开发模式下 `/content/**` 优先读 `events/`，找不到再落到 `content/` | 同一 URL 两个来源。zip 投放的验证会被 `events/` 遮蔽，"我投了怎么没生效"变成常规困惑，而这正是最难自查的一类问题 |

**选定**：目录 `events/`（入库，作者工作台），URL `/draft/**`（仅开发模式）。

### 决策 2：草稿挂载复用既有的内容托管管线

**备选**：使用框架自带的静态文件挂载直接指向 `events/`。

**否决理由**：会丢掉两件对本地验证至关重要的行为。

- 通配跨源许可头 —— 草稿页将读不到自己目录下的数据文件，而"活动页可以取自己目录的 JSON"是文档明确鼓励的用法。
- 返回文档时保证桥接脚本就位 —— 作者不写那一行就握不上手，表现是"活动页连不上宿主"，而根因在挂载方式。

这两种失败都会把排查引向错误方向：症状出现在活动页，原因在服务端配置。

**选定**：与 `/content` 同一条管线，只在"根目录"和"是否挂载"上不同。

### 决策 3：调试台用真宿主，调试逻辑放在观测与注入上

**备选**

| 备选 | 否决理由 |
|---|---|
| 调试台自己实现一套 postMessage 宿主 | 它就是**测试替身**。测替身只能证明替身是对的，不能证明真宿主是对的；两者的漂移是渐进的、不报错的，结果是本地通过而线上失败 —— 恰好是这套设施要消灭的那类问题 |
| 给宿主桥接类加可注入的接口端口 | 需要动生产代码。而它想要的能力（伪造任意响应）在 wire 层就能拿到（见决策 4），不值当为此在生产类上开口子 |

**选定**：调试台用与生产同一份宿主实现；"调试逻辑"只体现在三件事上 —— 旁听双向消息、主动注入宿主侧消息、按操作抢先应答。它自己的身份与主题来源可以被面板改写，但那是替换**输入**，不是替换宿主语义。

**补充：为"看得见结果"加一个只读观测回调。** 上面三条里"旁听双向消息"原本漏了一半 —— 入站（活动页 → 宿主）可以靠调试台自己挂 window 监听拿到，**出站（宿主 → 活动页）拿不到**，而任务要求"活动页发起一次请求后，面板中出现该请求与其结果"。结果是宿主发出的，没有观测点就永远看不到。

三条备选都不成立：

| 备选 | 否决理由 |
|---|---|
| 在调试台里包一层 `iframe.contentWindow.postMessage` | **做不到**：沙箱 iframe 不含 `allow-same-origin`，宿主对 `contentWindow` 的属性访问会抛 SecurityError。调用 `postMessage` 是允许的跨源操作，但**改写**它需要属性访问 |
| 让调试台自己当宿主（重写一套） | 见上面的首选理由：测替身证明不了真宿主 |
| 就此接受"看不到结果" | 那面板就只能显示请求、不能显示应答，而**应答才是错误码映射与请求关联的落点** —— 桥接最容易出错的地方恰好在这一半 |

因此在宿主上增加一个**只读**的 `onMessage?: (direction, envelope) => void`：入站在来源校验与信封校验之后调用，出站在真正 `postMessage` 的那一处调用。

它不是"可注入端口"：不参与任何决策、不改变任何分支、不提供替换 API 的入口，宿主的行为与不加它时逐字节相同。这与既有的 `pendingCount` / `isHandshaken` 两个"供测试观察内部状态"的取值是同一类东西 —— 生产代码上开一个**观测**口子，而不是开一个**行为**口子。

**缺少哪一步会使这条边界失效**：若这个回调日后被用来影响发送内容或跳过发送（比如"回调返回 false 就不发"），它就从一个观测口子变成了行为口子，调试台与生产宿主就不再是同一份实现了。因此它必须保持 `void` 返回、调用点在发送之前但结果被忽略。

### 决策 4：拦截用"抢先应答同 id 的结果"，而不是替换宿主的调用

**机制**：活动页侧 SDK 的待决表按请求 id 索引，**第一个到达的应答生效**，其后同 id 的应答因为查不到待决表而被静默忽略。因此调试台可以在宿主收到请求的那一刻，抢先回一个同 id 的结果。

**这条机制为什么值得写下来**：它是"不需要给生产代码开口子"的全部依据。缺少它，决策 3 的第二个备选就无法被否决。

**缺少哪一步会使该机制失效**：若活动页侧 SDK 改成"后到覆盖先到"，或按发送方窗口过滤应答，抢先应答立刻失效。此时必须回到"可注入的接口端口"方案。这一条要连同实现一起写进注释，否则将来改动 SDK 的人不会知道自己刚刚弄坏了什么。

**诚实记下代价**：伪造 `submit` 类结果时，真宿主**已经真的把请求发出去了**，后端仍会收到一次提交、也可能真的建一条记录。伪造治的是"活动页怎么渲染这个结果"，治不了副作用。要干净地测终态，仍然应该让后端真的拒绝你（把名额设成 0、把截止时间设到过去）。因此面板默认关闭拦截，并标明哪些请求是伪造的。

### 决策 5：iframe 来源限定站内路径

**备选**：接受任意地址，让使用者想指向哪里就指向哪里。

**否决理由**：宿主会把初始化消息（含身份描述符）交给被加载的页面，并把自己所在的活动变成该页面的操作代理。

**缺少哪一步会使这条边界失效**：只要少了"来源必须落在站内"这一步，调试台就变成一个开放代理 —— 它同时还在把当前登录用户的显示名与角色交给任意地址。身份描述符被刻意设计成零凭证（这正是它可以被交出去的原因），所以泄露的严重性有限，但它仍是个人信息，而"操作代理"是实打实的能力。

**选定**：只接受站内路径，站外直接拒绝。这与宿主既有的导航约束是同一条纪律 —— 那条也只接受站内路径。

另需说明一个能力边界：用 `srcdoc` 贴片段的那条路（方便"改一行看一眼"）下，页面处于没有基址的不透明源，**相对路径会断**。因此它只能用来试片段，不能用来试"读取自己目录下的数据文件"。

**本期不做 `srcdoc` 贴片段模式。** 备选是"面板里给一个 textarea，把贴进来的 HTML 直接用 `srcdoc` 装进 iframe"，否决理由有两条：

1. 相对路径断掉之后，它跑的是一个**与生产不同**的环境 —— 而"本地跑的就是线上那一套"正是这套设施存在的全部理由。一个只能试片段的入口会诱导人用它去验那些依赖相对资源的页面，然后在真正承载时失败。
2. 它会和一条既有的安全断言正面冲突：`sandbox.spec.ts` 有一条"用 `src` 挂载内容，而不是取 HTML 文本再注入"。`srcdoc` 严格说不是那个危险（沙箱 iframe 里的 `srcdoc` 仍是不透明源），但把"内联 HTML"这个动作放进同一棵树里，会让那条断言从"禁止注入"退化成"禁止注入，除了这一处"。

要迭代片段，改 `events/<name>/index.html` 再刷新即可 —— 那条路走的就是生产同款管线。若日后确实需要它，应当连同"相对路径怎么办"一起设计，而不是先加一个入口。

### 决策 6：生产排除用构建期条件 + 动态引入

**备选**

| 备选 | 否决理由 |
|---|---|
| 运行时开关（环境变量或隐藏入口） | 组件仍在生产产物里，与需求相反 |
| 把调试台做成独立构建入口 | 对"顺手打开看一下"太重，且它要自己处理路由与共享状态 |

**选定**：路由注册处用构建期常量守卫包住一条动态引入。

**缺少哪一步会使这条边界失效**：只要路由文件里出现对该组件的**静态**引入（哪怕只是为了取一个类型），组件就会被拉进产物，守卫形同虚设 —— 而且不会有任何报错，产物里就是多了一个块。

**这条必须实证，不能推断**：需要一次真实构建，并在产物中检索一个**只属于调试台**的标记串。该检索本身要做变异测试 —— 去掉守卫后必须能发现它；否则一个永远返回"没找到"的检索会给出全绿结论，什么也没证明。

### 决策 7：保留前缀清单加 `draft` 与 `develop`，且不随构建模式变化

**备选**：只在开发构建里保留 `develop`。

**否决理由**：清单是构建期常量。让它随构建模式变化，会使"哪些标识不能用作活动"在不同构建下不一致 —— 同一个标识在开发环境是活动、在生产环境是别的，这种不一致比多让出一个标识名更坏。

**代价**：活动 ID 不能再叫 `draft` 或 `develop`。与 `content`、`data`、`sdk` 已经付出的代价同类。

**这一条不是可选项，而是既有测试的硬约束**：路由测试从路由表推导清单，开发构建里 `/develop` 在路由表里，因此那条测试会要求 `develop` 已登记。`draft` 不同 —— 它由服务端处理、前端路由不注册它，所以测试不会强制它；把它登记进去是为了让清单成为完整的"平台保留字"（`api`、`content`、`data`、`sdk`、`assets` 都是这样进去的）。

### 决策 8：开发活动在启动时补齐，而不是靠脚本或手工发布

**备选**

| 备选 | 否决理由 |
|---|---|
| 仓库里的种子脚本 | 现有种子都在被版本控制排除的目录里，而调试台**依赖**这个活动的存在。让一个入库的功能依赖一个不入库的脚本是错的；换地方放又要新造一个脚本目录的约定 |
| 管理台手工发布 | 没有"开箱即用"，且每次换库都要重来一遍 —— 而这正是最容易被跳过的一步 |
| 活动配置声明在草稿目录里 | 本期不做（见 proposal 的不做项）：它把"配置"变成第二处真相 |

**选定**：启动时补齐，形状对齐既有的管理员引导：以库的状态为触发条件、幂等、只在开发模式生效。

**缺少哪一步会使这条边界失效**：这条补齐必须在非开发模式下**完全惰性**。守卫写漏的后果是：生产在空库启动时凭空造出一个**已发布**活动 —— 那是一个可被公开访问的平台内容面，且它在管理台上看起来像是有人建过的。因此需要一条断言直接钉住"非开发模式下不创建活动"。

### 决策 9：调试台的动作清单从协议常量推导

**备选**：在面板里手写一份按钮清单。

**否决理由**：仓库已有先例并写明了理由 —— 手写一份清单时，它只能断言"我列的这些都在"，而真正要防的是"加了新东西却忘了登记"，那种情况测试照样绿。协议里的宿主消息类型与操作白名单是这份清单的真源。

**选定**：从协议常量推导动作清单；协议里新增一个操作，面板上就自动出现对应入口。

### 决策 10：把作者工作流从投放目录迁到源码目录

**现状**：接入指南教人把活动页放进投放产物目录，然后按活动标识访问。而那个目录不入库，且下一次投放会整体替换它 —— 作者的工作台就是部署的目标位置。

**选定**：指南改为"放进 `events/<name>/`，访问 `/draft/<name>/`"。旧的投放目录路径仍然可用，但不再作为作者工作流介绍；同时说明两者的职责区别（源码 vs 产物）。

### 决策 11：拦截改为"挂起 → 选择"，并为此在宿主上开一个**行为**口子

决策 3 与 4 定的是"抢先应答"：面板在宿主收到请求的那一刻先回一条伪造结果，真宿主照常把请求发出去。它有一个当时就写明了的代价 —— **伪造治不了副作用**，后端仍会收到那次提交。

要求变了：拦截要能"观察请求内容，然后选择假响应**或**转发"。这两件事在抢先应答模型下都做不到：

| 想做的事 | 抢先应答模型下 |
|---|---|
| 先看清请求内容再决定 | 做不到 —— 你看到它的时候，它已经被发出去了 |
| "转发"成为一个**选择** | 不成立 —— 无论你选什么，请求都已经发出去了，"转发"退化成"什么都不做" |

所以必须能**拦住**请求。三条路：

| 备选 | 否决理由 |
|---|---|
| 继续用抢先应答，把"转发"实现成"不伪造" | 见上表：这不是一个选择，而是一个恒真的陈述。要求里的"选择转发"就没意义了 |
| 用 `dispose()` 停掉宿主来"拦住" | `dispose()` 只拒绝宿主自己的待决 promise，不给活动页回结果（这一点在实现期已经被实测到：活动页会永远卡在 `CEA.event()`）；而且它没有"稍后转发这一条"的入口 |
| 面板自己重写一套宿主 | 决策 3 已经否决过：测替身证明不了真宿主 |

**选定**：宿主上增加一对明确的挂起/结算接口 —— `shouldHold(op, args)` 判定是否挂起、`onHold(held)` 通知、`forwardHeld(requestId)` 转发、`failHeld(requestId, error)` 用伪造错误结算。被挂起的请求**不进网络**，等调用方决定。

**这与决策 3 补充里那个"只读观测口子"的约定是相反的，必须写清楚为什么可以反。** 那个口子当时约定"不得影响发送内容或跳过发送"，理由是"一旦如此，调试台与生产宿主就不再是同一份实现了"。这里的情况不同：

- 它**不是**"调试台有自己的宿主"，而是"宿主多了一个可选的拦截点"。不传 `shouldHold` 时，`handleRpc` 的路径与加它之前逐字节相同 —— 生产宿主（`event/EventView.vue`）**不传**。
- "同一份实现"要保的是**语义**（信封、操作白名单、错误码映射、超时、清理），这些一条都没变。变的只是"这一次要不要发出去"，而那是调用方显式要求的。

**缺少哪一步会使这条边界失效**：如果 `EventView` 哪天也传了 `shouldHold`，生产环境的请求就可能被**静默丢弃** —— 活动页那边表现为永远等不到结果，而服务端什么都没收到，没有任何日志。因此要有一条断言钉住"生产宿主不传这个口子"（读源码文本的断言，按仓库惯例配变异测试）。

**挂起也不该有超时。** 决策 4 里 RPC 的 30 秒超时对"等人做决定"是不合适的：人可能去看别的东西了。被挂起的请求因此**不进超时计时**，只在最终结算时才开始计时转发那一段。

### 决策 12：侧边调试台用 toolrail + 分页，而不是一列长滚动

原来的面板是一列从上到下堆叠的卡片，整体滚动。区块一多就要来回滚，而且"拦截"这块会随被挂起的请求增长，把日志挤得更远。

改为：一条**工具轨**（图标按钮）放在**最右侧**，它左边是内容区，内容按 tab 切换（状态 / 身份 / 动作 / 拦截 / 日志）。每页各自装得下，不再需要"滚动整块面板"。

顺序是 `iframe | 内容 | 轨`：轨贴着窗口右缘，分隔线与选中指示也一并镜像到右侧 —— 轨在右边时把指示条留在左边，它会紧贴内容区，看起来像内容区自己的边框。

- **日志页**仍然自己滚动 —— 它是流式内容，这是它的正常形态，与"整块面板滚动"不是一回事。
- **拦截页带角标**显示当前被挂起的请求条数：拦截是唯一需要"有人去做点什么"的页，不提示就会漏掉，而漏掉的请求会让活动页一直等着。
- 图标用内联 SVG + `currentColor`，与既有 `ToastHost.vue` 同一做法，不引入图标依赖。

## Risks / Trade-offs

- **伪造留下真实副作用**（伪造 `submit` 类结果时后端仍收到提交）→ 拦截默认关闭；界面标明被伪造的请求；文档写明伪造只改渲染、不改副作用。
- **把调试台的注入当成了宿主行为** → 因为复用真宿主，与生产的差异只可能来自注入的消息；面板把自己注入过的消息单独标出。
- **生产凭空多出一个已发布活动** → 守卫以运行模式为唯一判据，并有断言钉住非开发模式下不创建。
- **生产产物里仍含调试台** → 构建后检索只属于它的标记串，且该检索做变异测试。
- **草稿内容被误当作可投放内容** → 文档明确 `events/` 不是投放来源；`/draft` 在生产不存在，想投也投不了。
- **抢先应答随 SDK 演进失效** → 把失效条件写进实现注释；SDK 一改应答结算顺序，就回到可注入端口方案。
- **`draft` / `develop` 不能再作活动 ID** → 与既有保留前缀同类的已知代价，写进规格。
- **开发活动被当成真实数据源来做统计** → 它的存在本身就是开发事实；管理端可见，命名上须能一眼看出其用途。

## Migration Plan

- **无数据迁移**：开发活动由启动补齐，不是迁移脚本；生产库不会因此多任何行。
- **落地顺序**：后端（草稿挂载 + 启动补齐）→ 前端（代理 + 调试台）→ nginx（`/draft/` 明确 404）。顺序的理由是每一步都能单独验证。
- **回滚**：删掉调试台路由与 `events/` 即回到现状；`/content` 与线上内容全程不受影响。
- **生产影响面**：nginx 多一条 404 规则；前端产物少一个组件；后端多一个在非开发模式下惰性的分支。

## Open Questions

- 调试台面板的默认布局与信息密度 —— 留给实现时按实际观感定，不影响规格、方案与任务拆分。
- 面板是否值得内置一个"试读取草稿目录下 JSON"的动作，用来演示那条通配跨源许可头 —— 不影响规格与拆分。
