# Spec Delta

## Purpose

限制请求速率以保护服务与数据库，在不引入额外共享存储的前提下同时覆盖网络边缘与已登录用户维度，并保证被拒绝的请求与业务性拒绝可被区分。

## ADDED Requirements

### Requirement: 边缘层按来源限流
平台 MUST 在反向代理层按客户端来源地址限流。提交类端点与一般接口 MUST 使用不同的阈值，且提交类端点的阈值 MUST 更严格。超限请求 MUST 返回 429。

#### Scenario: 突发请求被限流
- **WHEN** 单一来源地址在短时间内连续发起远超阈值的请求
- **THEN** 超出部分的响应为 429

#### Scenario: 提交端点阈值更严格
- **WHEN** 分别以相同速率请求提交端点与一般读取接口
- **THEN** 提交端点先被限流

#### Scenario: 限流状态码正确
- **WHEN** 请求因边缘限流被拒绝
- **THEN** 响应状态为 429 而非 503

#### Scenario: 同一来源的突发被允许在突发额度内
- **WHEN** 请求速率短暂超过稳态阈值但未超过突发额度
- **THEN** 请求被正常处理

### Requirement: 应用层按来源与用户限流
应用层 SHALL 对提交与认证类端点限流。限流键 MUST 至少覆盖客户端来源；对已登录请求 MUST 额外覆盖用户维度。限流阈值与时间窗 MUST 可配置。

#### Scenario: 同一用户超过阈值被拒
- **WHEN** 同一已登录用户在时间窗内超过提交阈值
- **THEN** 后续请求返回 429，即使来源地址发生变化

#### Scenario: 同一来源多个账号受来源维度约束
- **WHEN** 同一来源地址下多个不同账号各自提交，累计超过来源维度阈值
- **THEN** 后续请求返回 429

#### Scenario: 认证端点受保护
- **WHEN** 同一来源在时间窗内大量请求登录或注册
- **THEN** 超限请求返回 429

#### Scenario: 阈值可配置
- **WHEN** 运维调整限流配置并重启服务
- **THEN** 生效的阈值随之改变

### Requirement: 转发头的信任边界
应用层 MUST 只信任来自反向代理的转发头。当请求并非来自受信任代理时，应用 MUST 忽略其中的客户端地址声明并以实际连接来源为准。

#### Scenario: 伪造转发头不改变限流键
- **WHEN** 客户端自行携带伪造的来源地址转发头请求提交端点
- **THEN** 限流键仍以实际连接来源计算

#### Scenario: 来自代理的转发头被采信
- **WHEN** 请求来自受信任代理且携带其写入的来源地址
- **THEN** 应用以该来源地址计算限流键

### Requirement: 限流拒绝与业务拒绝可区分
限流拒绝 MUST 使用 429 并 MAY 携带建议重试等待时间。限流拒绝 MUST 与名额已满（409）、活动已关闭（403）、需要登录（401）在状态码上区分，使客户端能判断是否值得重试。

#### Scenario: 限流与名额已满区分
- **WHEN** 请求分别因限流与因名额已满被拒绝
- **THEN** 两者返回的状态码不同，客户端可据此区分重试与终止

#### Scenario: 限流响应可携带等待时间
- **WHEN** 请求因限流被拒绝
- **THEN** 响应中可携带建议的等待时间

### Requirement: 应用层限流的部署前提
应用层限流的状态 MUST NOT 依赖数据库。在既定的单进程部署下其语义 MUST 正确；若部署改为多进程，平台 MUST 以文档明确其阈值将被按进程数放宽，或改由边缘层承担该职责。

#### Scenario: 限流不产生数据库写入
- **WHEN** 请求触发限流判断
- **THEN** 不产生任何数据库写入

#### Scenario: 单进程部署下限流精确
- **WHEN** 应用以单进程运行且请求超过阈值
- **THEN** 超出的请求数量与配置阈值一致

#### Scenario: 多进程部署的后果被记录
- **WHEN** 检视部署文档
- **THEN** 其中说明了多进程部署对应用层限流阈值的影响
