# Spec Delta

## Purpose

让管理员维护用户账号与权限，使开放注册引入的账号能够被查询、提权、停用，并在无邮件设施时仍能协助用户恢复访问。

## ADDED Requirements

### Requirement: 首次启动引导管理员
用户表为空时，平台 SHALL 在启动过程中自动创建一个管理员账号，使开放注册无法产生首个管理员的缺口被自动补齐。账号名与初始口令 MUST 可由环境变量覆盖；未提供初始口令时 MUST 生成高强度随机口令。该引导 MUST 仅在用户表为空时触发，MUST 在重复与并发启动下幂等，且 MUST 可被配置整体关闭。

随机生成的初始口令 MUST 只在创建该账号的那一次输出，MUST NOT 在其后的任何时间再次出现。当初始口令由环境变量提供时，平台 MUST NOT 输出该口令。

#### Scenario: 空库首次启动创建管理员
- **WHEN** 平台启动且用户表为空
- **THEN** 创建一个角色为管理员的账号，账号名取默认值或环境变量覆盖值

#### Scenario: 已有用户时不触发
- **WHEN** 平台启动且用户表中已存在任意用户
- **THEN** 不创建任何账号，即使当前不存在名为 admin 的账号

#### Scenario: 账号名与口令可由环境变量覆盖
- **WHEN** 环境变量指定了账号名与初始口令后启动空库
- **THEN** 创建的账号使用指定的账号名与口令，且该口令可用于登录

#### Scenario: 未提供口令时生成随机值
- **WHEN** 未提供初始口令的环境变量且用户表为空
- **THEN** 生成随机口令创建账号，该口令可用于登录

#### Scenario: 随机口令只输出一次
- **WHEN** 账号以随机口令创建后平台重启
- **THEN** 不再输出该口令，且任何接口都不返回它

#### Scenario: 环境变量提供口令时不输出口令
- **WHEN** 初始口令由环境变量提供
- **THEN** 启动输出中不包含该口令

#### Scenario: 重复与并发启动幂等
- **WHEN** 平台在用户表为空的同一数据库上被重复或并发启动
- **THEN** 至多存在一个由引导创建的管理员账号

#### Scenario: 引导可关闭
- **WHEN** 配置关闭了该引导且用户表为空
- **THEN** 不创建任何账号

### Requirement: 用户管理仅限管理员
用户管理相关接口 MUST 仅对 `admin` 角色开放。普通用户与匿名请求 MUST 被拒绝。

#### Scenario: 普通用户被拒绝
- **WHEN** 已登录的普通用户请求用户列表
- **THEN** 响应为 `403`

#### Scenario: 管理员可访问
- **WHEN** admin 请求用户列表
- **THEN** 返回用户数据

#### Scenario: 匿名被拒绝
- **WHEN** 未携带会话的请求访问用户管理接口
- **THEN** 响应为 `401`

### Requirement: 用户查询与筛选
管理员 SHALL 能够分页查询用户，并可按用户名、角色与启用状态筛选。响应 MUST NOT 包含口令哈希或会话凭据。

#### Scenario: 按角色筛选
- **WHEN** admin 以角色 `admin` 筛选用户列表
- **THEN** 结果只包含管理员账号

#### Scenario: 按启用状态筛选
- **WHEN** admin 以已停用状态筛选
- **THEN** 结果只包含被停用的账号

#### Scenario: 响应不泄露敏感字段
- **WHEN** 检视用户列表响应
- **THEN** 其中不含口令哈希、重置凭据或会话凭据

### Requirement: 角色变更
管理员 SHALL 能够将普通用户提升为管理员，或将其降级为普通用户。提权后该用户 MUST 立即获得管理接口的访问能力。

#### Scenario: 提权立即生效
- **WHEN** admin 将某普通用户提升为管理员
- **THEN** 该用户此后可访问管理接口，无需重新登录

#### Scenario: 降权立即生效
- **WHEN** admin 将某管理员降级为普通用户
- **THEN** 该用户此后的管理接口请求返回 `403`

#### Scenario: 不能移除最后一个管理员
- **WHEN** 系统中仅剩一个管理员，试图将其降级或停用
- **THEN** 操作被拒绝，以避免系统失去管理能力

### Requirement: 账号停用与启用
管理员 SHALL 能够停用与启用账号。停用 MUST 立即阻止该账号登录，并 MUST 使其既有会话失效。平台 MUST NOT 因停用而删除该账号的历史提交记录。

#### Scenario: 停用后无法登录
- **WHEN** 某账号被停用后该用户尝试登录
- **THEN** 登录被拒绝

#### Scenario: 停用后会话失效
- **WHEN** 某账号被停用而其用户当前已登录
- **THEN** 该用户的后续请求返回 401

#### Scenario: 历史提交保留
- **WHEN** 某账号被停用后管理员查看该用户此前的提交
- **THEN** 提交记录仍然存在且可见

#### Scenario: 重新启用可恢复使用
- **WHEN** 被停用的账号被重新启用
- **THEN** 该用户可再次登录

### Requirement: 签发重置令牌
管理员 SHALL 能够为指定用户签发一次性口令重置令牌。明文令牌 MUST 只在签发响应中出现一次，此后任何查询接口 MUST NOT 返回该明文。签发 MUST 被记录以便追溯。

#### Scenario: 签发返回一次性明文
- **WHEN** admin 为某用户签发重置令牌
- **THEN** 响应包含明文令牌与有效期

#### Scenario: 明文不再出现
- **WHEN** 管理员此后再次查询该用户或令牌列表
- **THEN** 响应中不含该明文令牌

#### Scenario: 签发需要用户存在
- **WHEN** admin 为不存在的用户签发令牌
- **THEN** 响应为 404

### Requirement: 批量角色与状态变更
管理员 SHALL 能通过一次请求变更一批用户的角色与／或启用状态。响应 MUST 给出**实际改动条数**；请求中找不到的 id MUST 被跳过，而不是让整批失败。

**最后管理员的判定 MUST 整批一起算。** 逐个检查会漏掉"一次降掉全部管理员"：第一次检查看到"还有另一个管理员在"而通过，第二次检查时第一次的改动尚未落库、同样通过 —— 结果一个可用管理员都不剩，系统永久失去管理能力。实现 MUST 先算出改完之后剩余的**可用管理员**（角色为 admin **且**已启用），不足一个时整批拒绝，且 MUST NOT 产生部分生效。

停用自己的检查同理：目标集合中含操作者本人且请求将其停用时，MUST 整批拒绝，而不是"改了一半才发现"。

角色或启用状态发生变化的用户，其会话 MUST 被吊销。

#### Scenario: 批量提权
- **WHEN** 管理员对多个普通用户提交批量改角色为 `admin`
- **THEN** 全部生效，响应给出改动条数

#### Scenario: 一次降掉全部管理员被拒绝
- **WHEN** 库中仅有的两个启用管理员被同一次请求一起降级
- **THEN** 请求被拒绝并返回 `last_admin_protected`，且**一条都未被改动**

#### Scenario: 还剩一个可用管理员时允许
- **WHEN** 库中有两个启用管理员，被降级的只是其中之一
- **THEN** 请求成功，且那一个确实变为普通用户

#### Scenario: 停用的管理员不算可用
- **WHEN** 除停用账号外仅剩一个启用管理员，且该账号被请求降级或停用
- **THEN** 请求被拒绝

#### Scenario: 不能停用自己
- **WHEN** 目标集合中包含操作者本人，且请求将其停用
- **THEN** 整批被拒绝，集合中其它用户 MUST NOT 被改动

#### Scenario: 未知 id 被跳过
- **WHEN** 请求中混入了不存在的用户 id
- **THEN** 请求成功，改动条数只计入实际存在的用户

#### Scenario: 权限变更立即吊销会话
- **WHEN** 某用户的角色经由批量请求被改变
- **THEN** 其既有会话立即失效，须重新登录后才以新角色行事
