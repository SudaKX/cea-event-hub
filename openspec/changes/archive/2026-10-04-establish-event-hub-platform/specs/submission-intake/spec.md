# Spec Delta

## Purpose

接收活动页提交的信息与文件，并提供幂等、可追溯、有容量边界的存储，使各活动无需自建后端即可收集报名与反馈数据及其附件。

## ADDED Requirements

### Requirement: 提交端点与请求形状
平台 SHALL 为每个活动提供两个提交端点：JSON 端点接受请求体本身即为提交内容；文件端点接受 `multipart/form-data`，其中可选的 `payload` 部分为 JSON 字符串、`files` 部分可重复出现以承载多个文件。分类标签 `kind` MUST 通过查询串传递。当一次提交同时包含字段与文件时，客户端 MUST 只调用文件端点一次并同时携带两者。

#### Scenario: 纯字段提交
- **WHEN** 客户端向 JSON 端点提交一个 JSON 对象
- **THEN** 受理成功并返回新建提交的标识

#### Scenario: 字段与文件合并为一次提交
- **WHEN** 客户端向文件端点同时提交 `payload` 与两个 `files`
- **THEN** 只产生一行提交记录，且该记录关联两个文件

#### Scenario: 纯文件提交
- **WHEN** 客户端向文件端点只提交 `files` 而不提交 `payload`
- **THEN** 受理成功，提交内容为空对象且关联所提交的文件

#### Scenario: 非 JSON 请求体被拒绝
- **WHEN** 客户端以表单编码而非 `application/json` 向 JSON 端点提交
- **THEN** 响应为 `415`

### Requirement: 提交内容与体积约束
提交内容 MUST 为 JSON 对象；序列化后 MUST NOT 超过配置的 `payload` 体积上限。单文件体积、单次请求文件数与单次请求总体积 MUST 受配置上限约束。超限请求 MUST 被拒绝且 MUST NOT 留下任何已落盘文件。

#### Scenario: 内容为数组时被拒绝
- **WHEN** 客户端提交的 JSON 顶层为数组或标量
- **THEN** 响应为 `422`，且不创建提交记录

#### Scenario: 内容超出体积上限被拒绝
- **WHEN** 序列化后的提交内容超过配置上限
- **THEN** 响应为 `422` 或 `413`，且不创建提交记录

#### Scenario: 单文件超出上限被拒绝
- **WHEN** 某个文件体积超过单文件上限
- **THEN** 整次提交被拒绝，且该请求中的任何文件都未被持久化

#### Scenario: 文件数超出上限被拒绝
- **WHEN** 单次请求携带的文件数超过配置上限
- **THEN** 整次提交被拒绝

### Requirement: 分类标签
`kind` SHALL 为可选的自由标签，平台 MUST NOT 对其做语义校验。平台 MUST 将其限制为 `[a-z0-9_-]` 且长度不超过 64；不符合时 MUST 回落到固定默认标签。平台 MUST NOT 允许该值影响持久化路径的任何上级目录。

#### Scenario: 合法标签被保留
- **WHEN** 客户端提交 `kind=signup`
- **THEN** 该提交的分类标签为 `signup`

#### Scenario: 非法标签回落到默认值
- **WHEN** 客户端提交的 `kind` 包含路径分隔符、点号或大写字母
- **THEN** 该提交的分类标签为默认值 `_default`，且文件未落到活动目录之外

#### Scenario: 未提供标签
- **WHEN** 客户端未提供 `kind`
- **THEN** 该提交的分类标签为默认值 `_default`

### Requirement: 提交者标识
每条提交 SHALL 记录一个统一的提交者标识。已登录提交时该标识 MUST 由服务端会话推导，客户端提供的值 MUST NOT 覆盖它。匿名提交时该标识 SHALL 取自客户端提供的匿名标识；未提供时 MUST 记为固定的未知标识。服务端 MUST NOT 将匿名标识用作任何鉴权判据。

#### Scenario: 登录提交以用户身份记录
- **WHEN** 已登录用户提交信息
- **THEN** 提交记录关联该用户，且提交者标识与用户绑定

#### Scenario: 匿名提交记录客户端标识
- **WHEN** 未登录客户端携带匿名标识提交
- **THEN** 提交记录保存该匿名标识且不关联任何用户

#### Scenario: 缺匿名标识时记为未知
- **WHEN** 未登录客户端未携带匿名标识
- **THEN** 提交记录的提交者标识为未知，且请求仍被受理

#### Scenario: 匿名标识不可用于读取他人提交
- **WHEN** 客户端仅凭一个匿名标识请求提交历史
- **THEN** 请求被拒绝，历史读取必须基于已登录会话

### Requirement: 幂等
客户端 MAY 通过 `Idempotency-Key` 请求头声明幂等键。同一活动内相同幂等键的重复请求 MUST 返回首次提交的结果，且 MUST NOT 新建提交记录。幂等检查 MUST 在配额检查之前执行。

平台 MUST NOT 依据内容相似度自动判定重复：内容相同但未提供幂等键的两次提交 MUST 被视为两次独立提交。按内容判定不看请求身份，误判时会把用户的提交连同附件静默丢弃，而用户会以为提交成功；重复记录则是可见且可恢复的。

#### Scenario: 重试返回首次结果
- **WHEN** 客户端以相同 `Idempotency-Key` 重复提交同一活动
- **THEN** 响应指向首次创建的提交标识，且提交总条数不变

#### Scenario: 重试不消耗配额
- **WHEN** 活动剩余名额为 1，客户端以相同幂等键重试一次已成功的提交
- **THEN** 请求成功返回原提交，且剩余名额仍为 1

#### Scenario: 不同幂等键产生独立记录
- **WHEN** 客户端以不同幂等键提交相同内容
- **THEN** 产生两条独立提交记录

#### Scenario: 内容相同但无幂等键时不去重
- **WHEN** 同一提交者两次提交完全相同的 JSON 内容且均未提供幂等键
- **THEN** 产生两条独立提交记录，第二次的 `deduplicated` 为 `false`

#### Scenario: 只更换附件不会被吞掉
- **WHEN** 同一提交者先以「表单 + 附件A」提交，再以「相同表单 + 附件B」提交
- **THEN** 两次都产生独立记录，两个附件都被保留

### Requirement: 匿名提交的提交者标识
匿名提交（非登录会话）MUST 携带非空的 `client_id`。缺失或仅含空白字符时 MUST 拒绝该请求并返回校验错误，MUST NOT 回落到一个共享的占位标识。

#### Scenario: 匿名提交缺少客户端标识
- **WHEN** 未登录的客户端提交且未提供 `client_id`
- **THEN** 请求被拒绝且不新建记录

#### Scenario: 客户端标识仅含空白
- **WHEN** 未登录的客户端提交且 `client_id` 为空白字符
- **THEN** 请求被拒绝，与缺失同等对待

### Requirement: 文件与元信息的一致性
每个文件 MUST 以其内容摘要与随机化文件名持久化，原始文件名 MUST 单独记录且 MUST NOT 参与路径构造。平台 MUST 在数据库提交失败时清除本次已写入的文件。进程异常中断遗留的未完成记录及其文件 MUST 能被后台清理任务回收。

#### Scenario: 数据库失败不留孤儿文件
- **WHEN** 文件已写入磁盘但数据库提交失败
- **THEN** 本次写入的文件被删除，活动提交总条数不增加

#### Scenario: 原始文件名不参与路径
- **WHEN** 客户端提交名为 `../../etc/passwd` 的文件
- **THEN** 该文件以随机化名称落在活动数据目录内，原始名称仅作为元信息保存

#### Scenario: 清理任务回收残留
- **WHEN** 存在超时仍未完成的落盘记录
- **THEN** 清理任务删除其文件与记录，且该活动配额计数不被其长期占用

#### Scenario: 文件元信息可查
- **WHEN** 管理员查看某条提交
- **THEN** 可看到每个文件的原始名称、类型、体积与内容摘要

### Requirement: 提交条数配额
对允许匿名提交的活动，平台 SHALL 限制该活动内的提交总条数（默认 4096）。限制 MUST 在并发提交下依然成立，即任何时刻实际存在的提交条数 MUST NOT 超过上限。达到上限后新的提交 MUST 被拒绝并返回 `409` 与错误码 `quota_exhausted`。删除提交 MUST 释放相应名额，写入失败 MUST NOT 占用名额。

#### Scenario: 达到上限后拒绝新提交
- **WHEN** 活动的提交条数已达到上限，客户端发起新提交
- **THEN** 响应为 `409` 且错误码为 `quota_exhausted`，且不创建新记录

#### Scenario: 并发提交不突破上限
- **WHEN** 活动仅剩一个名额，多个请求同时发起提交
- **THEN** 至多一个请求成功，其余返回 `409`，最终提交条数不超过上限

#### Scenario: 写入失败不占用名额
- **WHEN** 某次提交在占用名额后因写入失败而回滚
- **THEN** 该活动可用名额恢复为原值

#### Scenario: 幂等重试不占用额外名额
- **WHEN** 活动已满，客户端重试一次此前已成功的提交
- **THEN** 返回原提交结果而非 `409`，且名额保持为 0

#### Scenario: 需要登录的活动不受默认上限约束
- **WHEN** 活动要求登录且未单独设置条数上限
- **THEN** 该活动不受 4096 条默认上限约束

#### Scenario: 活动级覆盖生效
- **WHEN** 活动单独设置了条数上限
- **THEN** 拒绝阈值以该值为准

### Requirement: 单个提交者的份数上限
活动 MAY 通过 `max_per_submitter` 声明单个提交者最多能提交几份；为空表示不限，下限为 `1`。达到该上限的提交者再次提交时 MUST 被拒绝并返回 `409` 与错误码 `submitter_quota_exhausted`，且 MUST NOT 影响其他提交者。

该错误码 MUST 与活动满额的 `quota_exhausted` 区分开：活动满额是"整个活动没位置了"，个人满额是"你不能再交了，别人还可以" —— 二者可采取的行动完全不同。

**该限制在并发提交下 MUST 依然成立** —— 两个几乎同时到达、且都会越过上限的请求，MUST NOT 双双成功。拒绝 MUST 只落在超出上限的那些请求上，MUST NOT 殃及未超限的提交者。

**这条限制对匿名提交只是建议性的**：匿名提交者的标识来自客户端自报的 `client_id`，更换即可绕过。要获得可信的限制，活动 MUST 要求登录，此时标识为服务端的 `u:{user_id}`。管理界面 MUST 说明这一边界。

#### Scenario: 达到个人上限后拒绝
- **WHEN** 某提交者在活动下已达上限，再次提交
- **THEN** 响应为 `409` 且错误码为 `submitter_quota_exhausted`，且不创建新记录

#### Scenario: 其他提交者不受影响
- **WHEN** 某提交者已达上限，另一个提交者首次提交同一活动
- **THEN** 该提交被正常受理

#### Scenario: 并发提交不突破个人上限
- **WHEN** 某提交者仅剩一份余额，同一提交者的多个请求同时发起
- **THEN** 至多一个请求成功，最终该提交者的份数不超过上限

#### Scenario: 未设上限时仍维护计数
- **WHEN** 活动未声明 `max_per_submitter`，提交者完成多次提交
- **THEN** 该提交者的计数等于其实际提交条数，此后才设置上限时该计数立即生效

#### Scenario: 升级时按既有提交回填计数
- **WHEN** 升级到引入该限制的版本，库中已有某提交者的多条提交
- **THEN** 其计数等于既有条数，设置上限后不会放行超出上限的提交

#### Scenario: 删除提交退还个人名额
- **WHEN** 管理员删除某提交者的一条提交
- **THEN** 该提交者的计数减一；若因此低于上限，其可再次提交

#### Scenario: 幂等重试不重复计数
- **WHEN** 提交者以相同幂等键重试已成功的提交
- **THEN** 返回原提交结果，其计数保持不变

#### Scenario: 匿名提交的限制可被绕过
- **WHEN** 匿名活动的提交者更换 `client_id` 后再次提交
- **THEN** 该提交被受理 —— 这是已知且被接受的边界，可信的限制需要活动要求登录
