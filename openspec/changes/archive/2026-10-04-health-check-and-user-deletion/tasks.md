## 2. id 不复用

- [x] 2.1 写迁移给 `users.id` 加 `AUTOINCREMENT`（SQLite 上要重建表）。只改 id 的分配策略，既有行一字不动，因此没有回填；以"插入三个 → 删掉最大那个 → 再插入一个"观察新 id 与被删的不同、且迁移前后各表行数不变为验证 —— **已完成**。三处只有实测才能发现的细节：(1) `sqlite_autoincrement` 是**表级 dialect kwarg**，`autoincrement=True` 给不出这个关键字；(2) 走 `batch_alter_table(..., copy_from=...)` 会**丢掉**这个 kwarg —— 迁移跑成功、数据一条不少、`sqlite_master` 里却没有 `AUTOINCREMENT`，目的完全没达到，因此改为手写 DDL；(3) `AUTOINCREMENT` 要求主键**内联**在列上，不能同时再有表级 `PRIMARY KEY (id)`（否则报 "more than one primary key"）。已验证：升级后 `id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT`、五张依赖表行数一条不少、users 的 id 集合一致、删掉最大 id 后新插入**不再复用**；降级后形态回到与升级前逐字相同、复用行为也回来。验证全程只碰副本（真库 SHA256 前后一致）
- [x] 2.2 把该迁移的版本号加进 `tests/test_migrations.py` 的 `BATCH_STEPS`。这是**守着数据丢失的那一步**：`users` 被五处外键引用，而批处理重建表加外键打开的组合在本项目静默删过依赖行。**做变异验证**：临时去掉 `alembic/env.py` 里的外键禁用，`BATCH_STEPS` 回归必须变红 —— 如果它照样绿，这条回归其实没在守任何东西 —— **已完成**，并且发现原来的 `_seed` 造不出这类损坏：它只插了活动/提交/附件，没有用户、没有会话，而 `users` 重建时真正会被级联掉的是 `sessions` 与 `user_tokens`。补上之后变异复现了当年那次事故本身：`AssertionError: 升到 8d54ac924e60 之后数据丢了：{'events': 1, 'submissions': 0, 'submission_files': 0, ...}` —— 提交从 1 条变 0 条。另外补了 `_audit_columns`：三处 `SET NULL` 的列（真实列名是 `events.owner_id`、`submissions.user_id`、`submissions.reviewed_by`）被清空时**行数完全不变**，只数行数抓不到
- [x] 2.3 改 `docs/deployment.md` 的 MySQL 迁移复核项：加一条说明 `AUTO_INCREMENT` 计数器自 8.0 起持久化、更老版本重启后按 `max(id)+1` 重算而可能复用 id；以照该条能指出"迁到 MySQL 时要核对哪一件事"为验证 —— **已完成**，作为复核项第 7 条，写明了为什么这件事重要（`submitter` 是派生字符串、没有外键）以及旧版本上的替代办法
