# Design

## Context

动机见 `proposal.md`；行为契约见本变更的三份 delta 规格。

影响做法的现状：

- `app/api/v1/health.py` 现在返回 `{"status": "ok", "app": ..., "env": ...}` —— 三个值全部来自配置，**一次数据库都不碰**。
- `users.id` 与 `pending_registrations.id` 都是 `INTEGER PRIMARY KEY`，即 rowid 别名，**没有 `AUTOINCREMENT`**。已实测：删掉 id 最大的那一行再插入，新行拿回同一个 id。
- `submissions.submitter` 是派生字符串 `u:{user_id}` / `a:{client_id}`，**没有外键**（决策 7 刻意如此）。三处指向用户的审计列是 `ON DELETE SET NULL`：`events.owner_id`、`submissions.user_id`、`submissions.reviewed_by`；`sessions.user_id` 与 `user_tokens.user_id` 是 `ON DELETE CASCADE`。`submission_files` 上**没有**指向用户的列。也就是说这个 schema **当初就是按"用户会被删除"设计的**，缺的只是删除端点本身。
- `users` 被上述五处外键引用。SQLite 上给某列加 `AUTOINCREMENT` 必须**重建整张表**，而本项目在这一点上有一个已修复的伤疤：批处理模式重建表 + 外键打开，会**级联删掉所有依赖行**（当时把 26 条提交变成了 3 条）。修复在 `alembic/env.py` 的 `disable_sqlite_foreign_keys`，回归测试在 `tests/test_migrations.py` 的 `BATCH_STEPS`。
- 管理端的提交列表渲染走 `app/api/v1/admin.py` 的 `_render_submission`，它已经持有 session。

## Goals / Non-Goals

**Goals:**

- 健康检查成为**可信的部署与排障判据**：库不可达时说不可达，迁移没跑时看得出来。
- 账号可以被彻底移除，且**移除一个账号不会伤及社团收集的数据**，也不会污染此后的账号。

**Non-Goals:**

- 不引入存活/就绪双端点。本项目的部署面是 systemd + nginx，**没有任何编排器会分别消费这两个端点**，多加一个只是多一个没人调用的接口。
- 不改 `pending_registrations.id`。它也同样是 rowid 别名，但已无任何东西从它的 id 派生（注册邮件的幂等键已改为从令牌摘要取），改它要付一次表重建的代价而收益为零。
- 不做批量删除用户、不做历史提交的匿名化或清空。

## Decisions

### 决策 1：健康检查做真实往返，且不新增端点

**备选与否决理由：**

| 备选 | 否决理由 |
|---|---|
| 维持只报进程存活（现状） | 库挂了、迁移没跑、连接池耗尽，它都说 ok。部署文档把它当验收手段，等于没有验收 |
| 另加根路径 `/health` 迁就轮询者 | 见决策 2 |
| 存活 + 就绪两个端点 | 单进程单库，且调度面是 systemd —— 没有编排器会分别使用二者。**多一个没人调用的端点不是健壮性** |

端点返回 `200` 还是 `503`，取决于"服务能不能干活"，而不是取决于"连接是否建立"。这两种失败要**分开说**，因为运维要采取的动作完全不同：

| 情形 | 响应 | `database` 字段 | 运维该做什么 |
|---|---|---|---|
| 一切正常 | `200` | `ok` | 无事 |
| 连不上数据存储 | `503` | `unreachable` | 查数据库进程、磁盘、连接串 |
| 连得上，但迁移从未跑过（`alembic_version` 表都不存在） | `503` | `unmigrated` | 跑 `alembic upgrade head` |
| 连得上、也迁移过，但版本落后于代码 | `200` | `ok` | 计划一次迁移；服务当前还能干活 |

**这张表是写实现时才发现要拆的。** 初稿写的是"不可达时 503、可达时 200"，而"可达"这个判据太粗：一个迁移从未跑过的库**是可达的**，但它一张业务表都没有，服务根本无法处理请求。按初稿它会返回 200 与一个空版本号，而部署脚本看到 200 就放行 —— 那正是这个变更要消灭的那类"检查说 ok、服务其实不可用"。反过来，把"表不存在"笼统地标成 `unreachable` 也不诚实：库明明连得上，去查数据库进程只会白费功夫。

判据用 SQLAlchemy 的 `has_table` 而不是匹配驱动的报错文本：后者是方言相关的，换个库或换个驱动版本就会失效。

版本不一致本身只影响可观测性，不影响服务能力：落后的库通常仍能服务旧版本的接口，因此那是**计划一次迁移**的信号，不是 `503` 的理由。

响应同时给出**当前迁移版本**与**代码期望版本**，后者取自 Alembic 的脚本目录 —— 两个值来自彼此独立的来源（一个是库里的表，一个是磁盘上的脚本），因此"代码已部署、迁移没跑"会直接显示成两个不一致的版本号，而不必登服务器查库。

**代价要认下来：** 数据库短暂抖动时它会返回 503。这是正确行为而不是缺陷 —— 但监控侧应当把它当"可能有问题"的信号，而不是"立刻重启服务"的触发器。systemd 的 `Restart=on-failure` 只看进程退出码，不读健康端点，因此不会形成重启风暴。

**安全边界：这个端点是匿名的，因此响应必须只含状态。** 缺了"响应不得含凭据、绝对路径与用户数据"这一条，一个为排障而开的口子就变成对全网开放的信息泄露面 —— 而且它不在 `/api/**` 的鉴权范围里。规格里那条场景就是守着它的。

### 决策 2：只保留 `/api/v1/health`，不为打错路径的轮询者让路

日志里有几百条 `GET /health → 404`，来自某个打错路径的轮询者。

**备选与否决理由：**

| 备选 | 否决理由 |
|---|---|
| 加一个根路径 `/health` 消掉噪音 | 见下 |
| 改那个轮询者 | 它是谁并不清楚（浏览器扩展或某个监控工具），改不动别人的东西；但**接受这几百条 404** 是零成本选项 |
| **只保留既有路径，把它做真** | 选中 |

加根路径的代价是三处永久约束：`/health` 是顶层路径，按既有约定"保留前缀之外的顶层路径一律解释为活动标识"，不加进 `RESERVED_PREFIXES` 前端会把它当成一个叫 health 的活动；加了，就要为一个没有产品含义的路径维护一条保留规则；而 nginx 也得多一条 location，否则请求根本到不了后端。**为了让一个打错地址的客户端不再打错，要在三层各加一条约束** —— 收益与代价不成比例。

### 决策 3：`users.id` 加 `AUTOINCREMENT`，而不是在删除时改写提交者

**备选与否决理由：**

| 备选 | 否决理由 |
|---|---|
| 删除时把该用户的 `u:7` 批量改写成墓碑形态 | 让删除路径承担"可能上万行的改写"，且改的是历史数据；每条提交的标识此后有两种形态，读代码的人要同时理解两者 |
| 只软删（停用），不提供硬删 | 直接否掉了这次的需求：误注册、垃圾账号需要的是"不存在"，而不是"停用" |
| 单独维护一个不回收的 id 序列 | 比给表加一个 SQLite 内建语义多一套机制，收益相同 |
| **给 `users.id` 加 `AUTOINCREMENT`** | 选中。一次迁移，删除路径保持简单，`u:7` 之后**永远**指向那个被删的人 —— 它天然就是墓碑 |

**安全边界：这一步缺了，"新账号不继承被删账号的数据"就静默失效。** 失效的表现不是报错，而是：删掉一个 id 最大的人，下一个人注册就拿到同一个 id，于是他在"每人最多 N 份"上被莫名挡住、在提交列表里看到别人的东西。规格里那条"新账号不继承"的场景与它对应的测试就是守着这一步的。

**MySQL 侧的注意：** `AUTO_INCREMENT` 计数器自 8.0 起持久化，更老的版本重启后按 `max(id)+1` 重算，可能复用 id。这是迁移到 MySQL 时的复核项，写进部署文档而不是在这里解决。

### 决策 4：删除保留提交，且守卫与停用同源

**备选与否决理由：**

| 备选 | 否决理由 |
|---|---|
| 级联删除他的提交与附件 | 社团收集的数据不该因为一个人注销就消失；且这与既有的"停用不删历史提交"直接矛盾 |
| 把提交匿名化（清空 payload） | 那是合规需求，不是账号管理需求；混在一起会让"删除账号"变成一个语义模糊的动作 |

保留提交的代价是**署名从此不可考**（只剩编号），这正是决策 5 存在的理由。

守卫复用既有的 `_assert_not_last_admin`：不能删掉最后一个**可用**管理员，不能删自己 —— 与降级、停用同一条规则，不另起一套判断。删除写一条审计日志，与"签发重置令牌"的既有做法一致。

### 决策 5：提交者显示用一次批量解析

**备选与否决理由：**

| 备选 | 否决理由 |
|---|---|
| 每条提交查一次账号是否存在 | N+1；一页 50 条就是 50 次查询 |
| 在提交行上冗余一列记录"提交者已删" | 要在删除时回写所有历史行，与决策 3 否决的那个方案是同一个问题 |
| **渲染整页时一次批量查询** | 选中。与活动列表、批量审核的既有写法一致 —— 那里同样要求取回只走一次 `IN` |

解析放在 `admin.py` 已有的 `_render_submission` 附近：它已经持有 session，且是提交响应的唯一出口。

### 决策 6：不设"必须先停用才能删除"的门槛

**备选与否决理由：**

| 备选 | 否决理由 |
|---|---|
| 要求先停用、再删除 | 挡不住误操作 —— 两步都是点击，第二步照样会点错；反而让"忘了先停用"变成一种新的失败模式 |
| **直接删除，走应用自有的确认框** | 选中。与"删除活动"完全一致：一个专门的 danger 区域 + 确认框，文案说清会发生什么 |

**安全边界：删除不可逆，因此确认框不是装饰。** 缺了它（或把删除按钮做得与"停用"同等外观、与其它操作并排无区分），一次误点就永久毁掉一个账号，且**没有任何补救路径** —— 重新注册会是一个新 id、新账号，历史署名回不来。

### 决策 7：这条迁移必须进 `BATCH_STEPS`

给 `users.id` 加 `AUTOINCREMENT` 在 SQLite 上要重建表，而 `users` 被五处外键引用。本项目的批处理 + 外键组合曾经**静默删掉所有依赖行**，修复是把迁移连接的外键关掉，回归测试是 `BATCH_STEPS` 里逐个版本跑一遍。

**为什么是"加进回归名单"而不是别的守法的办法：**

| 备选 | 否决理由 |
|---|---|
| 靠迁移里手写 `PRAGMA foreign_keys=OFF` | 修的是这一条迁移；下一条重建表的迁移还会踩同一个坑。项目已经把修复放在 `alembic/env.py`，那里对**所有**迁移生效 |
| 迁移后跑一次行数比对当验收 | 一次性的人工动作，不是回归。下次有人再加一条重建表的迁移，没有任何东西会提醒他 |
| **把本迁移加进 `BATCH_STEPS` 回归** | 选中。这条回归逐个版本验证"重建表不删依赖行"，而它只有在**新迁移也进名单**时才对新迁移生效 |

**安全边界：缺了"把本迁移加进 `BATCH_STEPS`"这一步，数据丢失不会在任何测试里出现。** 那正是上次事故发生的方式：迁移跑成功、日志干净、数据少了一半。因此"加进 BATCH_STEPS"与迁移本身是同一件事的两半，不是可选的收尾 —— 任务 2.1 与 2.2 因此属于同一组。

## Risks / Trade-offs

**[深检查会在数据库抖动时返回 503]** → 这是它该做的；但监控配置要把它当预警而非重启触发器，部署文档里写明。systemd 不读它，因此不会自动重启。

**[重建 `users` 表有数据丢失风险]** → 外键在迁移连接上已禁用（既有修复），且本迁移进 `BATCH_STEPS` 回归；迁移前备份 `var/app.db`。

**[删除不可逆]** → 确认框 + 审计日志；"停用"仍是"成员退出"的常规答案，删除只用于"这个账号本就不该存在"。

**[健康检查会暴露迁移版本]** → 版本号本身是低敏信息，但它确实告诉观察者"这个部署落后了"。若判断这个信息不该公开，可以改成只返回一个布尔"迁移是否就位"，代价是排障时少一个线索。这是一处可以事后收紧的取舍。

**[提交者解析可能被将来的分页改动绕过]** → 用例守着"查询次数与页内条数无关"，与既有的批量审核同款断言。

## Migration Plan

1. 迁移在服务启动前执行（顺序见 `docs/deployment.md`）—— 本次迁移只改变 **id 的分配策略**，既有行一字不动，因此没有数据回填。
2. 回滚用 `alembic downgrade`。注意降级同样要重建一次表，且**降级之后 id 复用会回来**。
3. 该端点与删除接口都是新增能力，不改变既有接口的形状，可以先部署后端再部署前端。
